# AGENTS.md

Rules for AI agents (Claude Code, Codex, Copilot, …) working in this repo. Humans follow the same rules (`CONTRIBUTING.md`). Product context, the language rule and the principles are in `CLAUDE.md`; spec conventions in `.claude/rules/specs.md`; the domain model and glossary in `docs/specs/product/00-product-overview.md`.

## Before you start

1. Find the story or requirement in `docs/specs/product/` (IDs `US-…`, `FR-…`). No spec entry, no code: propose the spec change first. Before you build a route, operation or component, look it up in `docs/guides/reference/app.md` and the component inventory of `docs/guides/reference/design-system.md`; it may exist already.
2. Path-scoped rules for each package, the specs and the CI files are in `.claude/rules/*.md` (Claude Code loads them when you touch matching files; read them if you use another tool).
3. Check `.agents/skills/` for a playbook that fits the task (`spec-to-tests`, `add-core-operation`, …) and follow it instead of improvising.
4. Before every story or enabler, claim it: `make claim ISSUE=<n>`. It refuses (exit 1) when the issue has an assignee, a PR references it or an origin branch carries its story ID; otherwise it assigns you, sets the board status, pushes the branch and opens a draft PR with a "Handoff" section. `make board` shows who works on what. Never start a story that someone else has claimed; ask them (US-DEV-08). Issues labelled `report` (the pinned "Retro: Issue flow") are generated by a workflow and are never work items: do not claim, edit or close them (US-DEV-11).
5. Every change lives on a dedicated short-lived branch (one task, one worktree) from `dev` and enters `dev` through a pull request: `make worktree BRANCH=<branch printed by make claim>` (the claim check runs again; opt-out only with an explicit `SKIP_CLAIM_CHECK=1`). Keep the "Handoff" section of the draft PR current. Never work in a directory another session uses.
6. Create issues only with `make issue TYPE=<type> EPIC=<code> PRIORITY=<P0-P3> TITLE="…" BODY=<file.md>` (FR-DEV-10). It refuses unknown values before it creates anything, and it sets the type and epic labels and the board fields Typ, Epic, Priority, Release and Status (Todo). The Release follows the rule of FR-DEV-10 (a bug by its priority, an epic none, every other type R2); `RELEASE=<code>` (for example `RELEASE=R3`) overrides it. Pick the priority by the rule of thumb in `docs/guides/operations/parallel-work.md` ("Priority"). Do not create issues with a bare `gh issue create`. An issue without exactly one type label and one epic label gets `needs-triage` and a comment, and `make claim` refuses it. A new type or epic is a pull request to `app/config/project/issue-taxonomy.json` that the owner merges.

## While you work

- Architecture is checked by scripts, not by goodwill: `core` has no I/O (AB-1), API and web import `core` only through `@pflanzendex/core` (AB-2), web talks to the database only over HTTP (AB-6). Writes go through validating operations (P-03). Tenant isolation is tested for every table (P-04).
- Tests come from the acceptance criteria and carry the story ID in their name (P-06).
- The file layout is checked by `make layout`: a size hint of 8 <!-- gate: layout.config.mjs#default.maxUnits --> units per directory (above it a hint, no failure); a folder without a manifest fails above 16 <!-- gate: layout.config.mjs#default.failUnits --> units; a `README.md` manifest (frontmatter with `expect`) allows the units it names; kebab-case names and one folder per component stay hard (`app/config/lint/layout.config.mjs`; the guide is `docs/guides/reference/file-layout.md`). A new violation fails the gate; the baseline `app/config/gates/baselines/layout-baseline.json` only shrinks. Move files with the layout rules in mind instead of adding to a crowded directory (FR-QG-21).
- Domain errors carry a stable code `<domain>.<reason>` with a text in `ERROR_TEXTS` (FR-QG-11). Nothing is swallowed silently (P-10).
- Language: the rule is in `CLAUDE.md` ("Language", ADR 0004). Write new and touched English text by the rules in `docs/writing-english.md` (ASD-STE100 writing rules, E-32).

## Gates you must not weaken

Gate configs (workflows, rulesets, git hooks, `Makefile`, ESLint/knip/commitlint/release configs, check scripts, thresholds, exception lists, `.claude/`) define what "done" means. The Claude Code hooks in `.claude/settings.json` ask a human before the first edit of each gate file on a branch; later edits of that file on the same branch pass (US-QG-07). Gate tests are the tests (`*.test.mjs`, `*.test.ts`, `*.test.js`, `*.selftest.mjs`) of gate and check code only: `.claude/hooks/`, `app/tools/check/`, `tools/lint/`, `make merge` (`app/tools/workflow/merge-pr.*`) and `app/tools/workflow/actions/ci-reuse/` (CI reuse, verdict and quarantine, gate review); the one list is `isGateFile` in `.claude/hooks/rules.mjs` (owner decision 2026-11-16, issue 2222). A gate test asks no question in the hook; `make merge` still refuses a PR that changes one, so a human reviews it there. App tests and the tests of product and process tooling are no gate files: agents merge them. Shell commands that name a hook record (`claude-gate*`) are refused, and so is a Write or Edit outside `.claude/hooks/` whose new text names one, docs included: name the records as `claude-gate*`. A ticket declares the gate files it will change with `make gate-plan FILES="…"` before its first gate edit, so that one human answer covers the whole list; an agent can propose a list but never confirm it (issue 1608, US-QG-07). Never change them to turn a red run green. If a rule is wrong, say so and change it in its own PR with a reason (US-QG-07). Until R1 is released, add a new gate only when an incident, defect or review finding asks for it and its issue names that finding; making an existing gate faster or more deterministic stays allowed (E-30 in `docs/specs/product/16-releases-and-decisions.md`).

`make setup` activates the git hooks in `.githooks/`: `commit-msg` (commitlint), `pre-commit` (Prettier and ESLint on staged files), `pre-push` (`make gates`). Blocked for agents (and pointless anyway, because CI and the rulesets repeat every check): `--no-verify`, force pushes, pushes to `dev` or `main`, calling `gh pr merge` directly, merging into `main`, changing `core.hooksPath`, editing rulesets or creating releases by hand. `git reset --hard` and `git clean` run only in a worktree, never in the main checkout, where they destroy uncommitted work (US-QG-07); the Claude Code hook refuses them there.

## Before you say "done"

1. `make ci` (or at least `make gates` plus the tests you touched) and report the result honestly: pass or fail, with the failing output. Never "should work" (D-05). The Stop hook reminds you if code changed after the last run.
2. Update the spec status (⬜ → 🟨 → ✅) and the counters in `docs/specs/product/readme.md` in the same PR. Name what you added in the reference docs, so the next agent finds it instead of building it twice: API routes and core operations in `docs/guides/reference/app.md`, shared UI components in the inventory of `docs/guides/reference/design-system.md`. `make reference-check` (part of `make gates`) enforces it; its baseline only shrinks (US-QG-10).
3. Commit only when asked. Conventional Commits with an epic scope, e.g. `feat(soz)`, and `docs:` for documentation; the allowed types and scopes are in `app/config/project/commitlint.config.js`. The PR title is checked the same way, because the squash merge turns it into the commit message. Open the PR against `dev` and fill in the template, including the "AI involvement" section; `make pr PR=<n>` pushes and marks it ready for review (US-DEV-13). A pull request that changes a gate file carries the label `owner-merge`: the workflow `owner-merge-label.yml` sets it on every push and removes it when no gate file is left; find them with `label:owner-merge`. `Closes #n` in the PR body closes the issue only when the PR reaches `main`, the default branch, and links the PR to the board status (`project-status.yml`); a PR for a partial step uses `Refs #n`. The README statistics are regenerated once per release PR, not per PR.
4. `main` holds the finished, released product, `dev` the current development state; neither gets direct commits (E-13). Merge into `dev` with `make merge PR=<n>` once `ci-status` is green: it squashes into `dev` and refuses unless the PR names a story that exists in `docs/specs/product/`, targets `dev`, and changes no gate file; then a human merges (ADR 0005). Releases go from `dev` into `main` through a pull request with a merge commit and stay with a human.
