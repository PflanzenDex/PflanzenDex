# Device checks (US-DEV-01, issue 2504)

`make device-check` runs one screen or one scripted flow on a matrix of devices, themes and text sizes, and writes a run folder with screenshots and a summary. It is a tool for people and agents, not a CI gate: it blocks nothing. Package `packages/e2e`, project `device-check`, spec `tests/accessibility/display/display-checks.device.spec.ts`; the self-tests of the pure parts are the two sibling specs `display-checks.device.self*.spec.ts` (no browser).

- **Filters** (comma lists; a run needs `SCREEN` or `FLOW`): `SCREEN=<id>` takes the ids of `support/display/screens.json`; `FLOW=<name>` takes the flows under `support/device-check/flows/`; `DEVICE=iphone16,oneplus15r,large,phone` (default: the three emulated devices; `phone` is the attached Android phone, local only); `THEME=light,dark` and `TEXT=100,200` (default: both); `FORCED=1` turns on forced colors. An unknown value is refused before anything starts, and the message names the valid values and a close match. A run over the whole register is refused.
- **Examples:** `make device-check SCREEN=today` (12 cells: 3 devices, 2 themes, 2 text sizes); `make device-check FLOW=water-plant DEVICE=iphone16 THEME=dark TEXT=200`; `make device-check SCREEN=today DEVICE=phone`.
- **Output:** `packages/e2e/device-check-report/<timestamp>/` (gitignored). `summary.md` and `summary.json` hold one row per cell: its status, the device as measured (model and window for the phone), every check with its measured value and detail, the screenshots, and what the tool does not check. Screenshots are `shots/<id>-<device>-<theme>-<text>-screen.png`, and `-after.png` after a flow. The command prints the summary path and a short table. Exit 1 when a check fails or a cell stops on an error. A phone that is not attached, or whose Chrome is not reachable, is a skipped cell with its reason, and the run exits 0. A cell whose test timed out or crashed still gets an error record with the reason.
- **Checks on every cell:** no horizontal overflow; the size floors of `judge.size.ts` (picture, row, name); the root font size of the text size (32 px at 200 %). A flow adds its own checks from `support/device-check/check.ts`: nothing moves under the finger (the named controls compared before and after), the page height does not change, the focus is not on the body, no toast for a success, and the result is in an aria-live region.
- **Flows:** one file each, found automatically: `flows/<area>/<name>.flow.ts` default-exports `defineFlow({ name, title, screen, run })`. Today: `water-plant` (SG-FEED-05, issue 2462), `friend-request` (SG-FEED-04 and SG-BASE-01, issue 2464) and `zone-delete` (SG-BASE-01, issue 2465). The `run` gets `page`, `check`, `shot`, `signedIn(account)` (the sign-in state of another demo account, for a second browser context) and the device, theme and text size of the cell. An area folder holds at most five flows (layout rule).
- **Real phone** (`DEVICE=phone`, local only, never CI): adb finds the phone; `adb forward tcp:9222 localabstract:chrome_devtools_remote` and `adb reverse` for the web, API and Keycloak ports; Playwright connects over CDP once per cell; the navigator.onLine shim of PF-040 is applied; the night mode follows the theme and is put back at the end, also after a failure. The summary names the model and the window.
- **Run times** (measured on the devbox on 2026-11-26, the whole `make` call with the demo seed and the build): one screen on one device, one theme and one text size, about 16 s; one screen on the whole matrix (12 cells), about 27 s, each emulated cell 3 to 9 s; one flow on one device, one theme and one text size, about 40 s (a cell of the friend-request flow takes 25 s). Three flows on one device took 4 min 9 s in the first run, because the friend-request flow waited out its timeout before it was fixed. A chunk of a fix (one page or one flow on the four-device matrix, both themes, both text sizes) is about 2 to 3 min by this measure. The real phone, one screen and one theme and text size: about 1 min 50 s, most of it the sign-in on the phone (the cell itself takes about 3 s).
- **Known limits:** TalkBack and other screen readers are checked by hand; the tool checks focus and announcements, not speech. The emulated devices are Chromium in the pinned browser container, not the phones. The real phone runs only on the devbox. Flows that write (watering, creating a zone, sending a friend request) change the demo data, and every run reseeds the demo first. On the real phone there is no second browser context, so a flow that needs another account's session (`friend-request`) fails its check there.
