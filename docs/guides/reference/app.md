# PflanzenDex app

Monorepo (npm workspaces) with four packages. Every task runs through the `Makefile` in the repo root (`make help`). Tooling and docs are English; domain code uses the German glossary terms from the specs (`account`, `specimen`, `review_case`, …).

This file is the index of what the API and `core` offer: look up a route or operation here before you build one. A new API route is named as `METHOD /path` and a new core operation as `domain.verb` in the section of its story; `make reference-check` enforces it, and the routes and operations from before the rule wait in `app/config/gates/baselines/reference-baseline.json` until their section names them (US-QG-10). Shared UI components are listed in the component inventory of `design-system.md` (section 4.4).

| Package         | Contents                                        | Rule                                                                                                                                            |
| --------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/core` | Domain logic, pure functions                    | imports nothing from API, web, database, file system or network (AB-1); every directory with code has an `index.ts`                             |
| `packages/db`   | PostgreSQL schema, migrations, tenant isolation | meant for `api` only; `core` and `web` never import it; every user-owned table carries `account_id` and calls `tenant_protection()` (FR-ACC-02) |
| `packages/api`  | HTTP API (Hono)                                 | calls `core` only through `@pflanzendex/core` (AB-2)                                                                                            |
| `packages/web`  | Mobile-first PWA (React, Vite)                  | calls `core` only through `@pflanzendex/core` (AB-2)                                                                                            |

## Modules (ADR 0003, variant A)

Inside each layer package the code is cut into module folders with the same names: `src/<module>/` in `core`, `db`, `api` and `web`. Each module has an `index.ts` as its public interface; other modules and the layer root import only from there. Test files sit next to the code. Migrations stay one global sequence (`packages/db/migrations/`, files `0001`-`0004` keep their names).

| Module       | Contents                                                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kernel`     | Operation engine, `Result`, error codes, validation, ports (`core/src/kernel`, with `meta`); tenant access, migrations, idempotency (`db/src/kernel`); error mapping (`api/src/kernel`) |
| `account`    | Sign-in and account (`core/src/account`, `db/src/account`, `api/src/account` incl. `auth/`, `web/src/account`); tables `account_data`, `account_role`                                   |
| `catalog`    | Review status (`core/src/catalog`, `db/src/catalog`); table `review_case`                                                                                                               |
| `light`      | Light zones and locations (`core/src/light`, `db/src/light`, `api/src/light`, `web/src/light`); tables `lightZone`, `location`                                                          |
| `collection` | specimens (`core/src/collection`, `db/src/collection`, `api/src/collection`, `web/src/collection`); table `specimen`; depends on `kernel`, `catalog`, `light`                           |
| `care`       | Care phases (`core/src/care`, `api/src/care`, `web/src/care`); no table yet (derived live); depends on `kernel`, `catalog`, `light`, `collection`, `monitoring` (registered)            |

```bash
make setup   # install dependencies
make dev     # start API and web (Vite): 3000 and 5173; in a worktree its own ports from .env.worktree (parallel-work.md)
make ci      # all gates: lint, types, boundaries, format, tests, build; every part runs, the failed ones are listed at the end
```

- **Node:** version 26 (`.nvmrc`). Vitest 5 does not officially support odd Node versions (e.g. 25).
- **Docker:** must run for `make workflows` (actionlint with shellcheck, in the image `rhysd/actionlint` pinned by tag and digest in `tools/lint/actionlint.sh`; CI runs the same script), and therefore for `make gates` and the pre-push hook. Without Docker it fails with a message; it never skips shellcheck. The test database (`make db-up`) needs Docker too.
- **TypeScript 6.0.x** is pinned on purpose: `typescript-eslint` does not support TypeScript 7 yet (peer range `<6.1`).
- **Exact versions:** every `package.json` names exact versions, never `^`/`~` ranges (`app/.npmrc` sets `save-exact`, Renovate uses `rangeStrategy: "pin"`). Workspace packages (`@pflanzendex/*`) stay `*`, which means the local workspace. Vulnerable transitive dependencies are fixed by updating the parent or refreshing the lock file, never with `overrides`; when no parent release has the fix yet, the advisory gets a dated entry in `config/gates/audit-allowlist.json` (QG-S2).
- **Load measurement (NFR-12):** `npm run perf:measure -w @pflanzendex/api` (`perf/load/measure.ts`) seeds accounts with 100 and 1,000 specimens in a throw-away test database and prints response times and SQL statement counts per request as JSON. `npm run perf:concurrency -w @pflanzendex/api` (`perf/load/concurrency.ts`, #1242) runs the Heute screen for 1 to 32 virtual users at the same time on the production pool (`PFLANZENDEX_DB_POOL_MAX` sets its size) and prints screens per second, median and p95. Both are measurements, not gates, and not part of `make ci`; results: `docs/records/test-logs/nfr-12.md`.
- **Boundary check:** `npm run boundaries` (script and tests in `scripts/`); messages name the rule ID, file and line. Module rules AB-7 to AB-14 (FR-QG-19) read the module register `modules.config.mjs`; AB-10 and table ownership run in `findSchemaViolations` (db tests). Layer rules AB-3 (AI layer calls operations only), AB-4 (Pokédex build job writes only its tree store) and AB-5 (foreign accounts only through the sharing layer, i.e. the `friend_*` functions of their owner module) run in `tools/check/code/modules/rules/check-layer-rules.mjs` and `check-sharing-layer.mjs` (FR-QG-05); self-tests in `check-layer-rules.test.mjs`.
- **Web layers (AB-15, FR-QG-23):** `app -> modules -> shared` below `packages/web/src/`: shared imports no module and not app, a module imports not app. The layer of a path comes from one mapping, `WEB_LAYERS` in `config/lint/module-rules.config.mjs` (folders `app/`, `shared/` and `styles/`; the collector cards are in the `pokedex` module since FR-QG-23 step 4, `components/` is gone). `npm run boundaries` fails on every finding with rule ID, file and line (blocking since FR-QG-23 step 5). The web kernel is `shared/data`: `KERNEL_FOLDERS` in the same config points the AB-11 glossary check there. Code in `modules/rules/check-modules-graph.mjs`, self-tests in `check-modules-graph.test.mjs`.
- **Layout fix and moves:** `make layout-fix DIR=<dir>` brings one directory within the layout rules (grouping by name prefix, `ARGS="--kebab"`, `ARGS="--into folder=name,prefix*"`); `make layout-fix ARGS="--move <from>=<to>"` (repeatable; repo-relative paths, a file or a directory) moves with `git mv` and rewrites every import that points at a moved file, relative and the web `@/` alias, in moved and other files. Dry run by default (prints the plan), `APPLY=1` applies; if a rewritten import would not resolve to the same file as before, nothing is changed. Mentions in strings, configs and docs are only listed ("check by hand"). The variable is `DIR`, not `PATH`, because `make` exports command-line variables and `PATH=` would replace the shell search path. Code in `tools/layout-fix/` (`fix-move.mjs` holds the shared rewrite and the move mode), tests `fix-move.test.mjs`.
- **Thresholds** (starting values, assumptions, E-15): file length ≤ 200, complexity ≤ 15, in `core` ≤ 10 (`eslint.config.js`).

## Initial JavaScript of the web app (QG-U6, DS-08, US-QS-14)

- Gate and report: `make bundle-report` lists the initial JavaScript per chunk and package; the budget gate (`bundle-budget`) fails above its limit. Keep new code out of the first load instead of raising the limit.
- **Lazy parts:** every page and destination area (`lazy-areas.ts`, the `lazyPage` exports of each module), the route table itself (`AppRoutes` in `app/routes.tsx`, loaded by `app/frame/app/app.tsx` and prefetched while the session loads, so the sign-in screens do not carry it), the OIDC client and the heavy sections. Only the shell, the entry screens, the navigation and the shared states stay in the first load.
- **Rule: a new page is added per `React.lazy`**, through `lazyPage` (`shared/platform/routing/lazy-page`), and rendered inside a `RouteBoundary`. It shows the skeleton while the chunk loads and "Erneut versuchen" when the chunk cannot be fetched (P-10). Do not import a page, area or heavy library statically from the shell, the navigation or `app/routes.tsx`. A page that a destination renders on its first visit is also listed in `destinationPages()` (`app/destinations/area-parts/lazy-areas.ts`), so its chunk is in hand before the visit (issue 1645, DS-72).
- **Preloading (issue 1645):** `shared/platform/routing/lazy-page/preload.ts` requests pages ahead of their render: `preloadWhenIdle` (batches, each once the shell is idle), `preloadPages` (now, each page once) and `usePreloadOnIntent` (a pressed or focused link). `useDestinationPreload` in `lazy-areas.ts` wires the bottom-bar destinations and the new-plant form into `AppRoutes`.
- **Class merging (`cn`):** `shared/lib/class-merge/merge-config.ts` is a subset of the tailwind-merge default config (about 4 kB gzip smaller than the full config). `class-merge.test.ts` fails when a Tailwind class used in `src` has a group in the default config that the subset lacks: copy that group (and its conflicts) over from the tailwind-merge default config.

## Database and tenant isolation (TE-02)

- **Test database:** `make db-up` starts PostgreSQL 18 in Docker (port 54329; `make test` and `make ci` do this themselves, in CI it runs as a service). Another server: `PFLANZENDEX_TEST_DATABASE_URL`. The database is throw-away, so every start runs it with `fsync`, `synchronous_commit` and `full_page_writes` off (issue 1636: a `DROP DATABASE` checkpoint took 18-19 s and the API suite 46-65 s; with the settings off 0.1 s and 31 s). An existing container gets them on the next `make db-up`; in CI, each job with a Postgres service runs `make ci-db-tune` after checkout, which sets the same three on that service container (issue 1698).
- **Test database owner (#294, QG-D1):** `PFLANZENDEX_TEST_DATABASE_URL` is the cluster superuser, which bypasses row-level security. The `db` suite therefore does not use it: the vitest global setup (`packages/db/src/test-global-setup.ts`) creates the login role `pflanzendex_test_owner` (no superuser, no BYPASSRLS) and the database `<name>_owner` it owns, and every test connects with `openOwnerPool()`, so row security applies to every query as in production. The superuser is used only where a test deliberately works across tenants or needs superuser-only settings: `openFixturePool()` (fixture helpers in `src/fixtures.ts`, cleanup and observation of forced tables in tests, the `observer` argument of `checkTenantIsolation`) and `openAdminPool()` (scratch databases and roles). `rls-guard.test.ts` fails if the suite connection ever becomes a superuser. The `api` suite does the same (#476): its vitest global setup (`packages/api/src/test-global-setup.ts`, #485) creates the owner role first, its test files open `openOwnerPool()` plus `openFixturePool()` for setup, cleanup and cross-tenant observation; `packages/api/src/rls-guard.test.ts` fails if the api suite connection becomes a superuser.
- **Migrations:** SQL files in `packages/db/migrations/`, forward only, with a checksum (an applied file must never change). Apply with `make migrate`. Every migration after `0012` runs in `realistic-migration.test.ts` over a fixture of prototype size (2 accounts, 13 species, 17 specimens with locations and zones, measurement series), which checks counts, values, references and tenant isolation afterwards (US-DEV-07); a new migration is covered by adding its file, nothing else.
- **New user-owned table:** column `account_id uuid not null references account(id) on delete cascade`, then `select tenant_protection('table');` and an entry in `packages/db/src/<module>/fixtures.ts` (aggregated in `packages/db/src/fixtures.ts`). If any of these is missing, the generic test (`tenant.test.ts`) fails. Tables without an account (e.g. the species catalog) need an entry with a reason in `WITHOUT_ACCOUNT_ID`.
- **Access:** only through `withAccount(pool, accountId, …)`: a transaction, role `pflanzendex_app` (without BYPASSRLS), session variable `app.account_id` for that transaction only.
- **Pool and time limits (NFR-12, #1242, starting values, assumptions):** `openPool(url, allowExitOnIdle, config)` (`kernel/connection/connection.ts`); the api gets its settings from `poolConfigFromEnv(process.env)` (`kernel/connection/limits.ts`): `PFLANZENDEX_DB_POOL_MAX` (default 12 connections, `PRODUCTION_POOL_MAX`), `PFLANZENDEX_DB_CONNECT_TIMEOUT_MS` (5000), `PFLANZENDEX_DB_STATEMENT_TIMEOUT_MS` (5000), `PFLANZENDEX_DB_LOCK_TIMEOUT_MS` (3000), `PFLANZENDEX_DB_IDLE_TRANSACTION_TIMEOUT_MS` (30000); 0 switches a limit off. Every transaction of the application role opens in one round trip (NFR-12, #1240): `beginAsApplicationRole` (`kernel/tenant.ts`) sends `begin`, the role switch and the transaction-local `set_config(..., true)` settings (the account or subject variable, `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`) as one simple-protocol query, every value escaped with `client.escapeLiteral`, so they end with the transaction. The query-count gate and the load harness count that opening as frame, because its text starts with `begin` (`query-count-statements.ts`, `api/perf/harness.ts`). `enterApplicationRole` does the switch and the settings in two statements, for a caller that runs something between `begin` and the switch (the catalog load, after its advisory lock). `withLongAccount` (account export, account deletion) and the catalog load use `LONG_LIMITS` (10 minutes per statement, 30 s lock, 10 minutes idle). Jobs and the taxonomy check run as the schema owner and have no statement limit. Operations: `docs/guides/operations/staging-deploy-and-backup.md`, section "Database pool and time limits".
- **The transaction frame (NFR-12, P-04, P-10, #1314):** every production path that takes its own connection runs through `settleTransaction(pool, open, work)` or `inTransaction(pool, open, body)` (`kernel/connection/transaction.ts`): `open` is `beginAsApplicationRole` or `beginPlain`, `work` answers `{ commit, value }`, `body` always commits. A failed rollback never replaces the answer or the original error, and that connection is dropped instead of going back to the pool. Do not write `begin`, `rollback` and `release` by hand in a new path. `migrate` keeps its own transactions on one session-locked connection. Tests: `transaction-rollback.test.ts`.
- **Stable codes for the database (NFR-12, FR-QG-11):** `system.database_unavailable` (503): a statement or lock exceeded its limit, no connection became free in time, or the server cannot be reached (`isDatabaseUnavailable` in `kernel/connection/limits.ts`). The API answers it for requests (`app.ts`, `onError`) and inside an operation (`answeredFailure` in `kernel/route-helpers.ts`), where it replaces `system.unexpected`. Any other failure no route answered is `system.unexpected` with status 500 (never a bare text). Tests: `src/database-limits.test.ts`, `kernel/connection/limits.test.ts`.
- **Taxonomy statistics (NFR-12):** `TaxonomyPostgres.replace` runs `analyze taxon` inside its transaction, after the whole tree is written (test: `pokedex/taxonomy.test.ts`, "NFR-12 the replacement runs ANALYZE").

## Indexes for the hot queries (NFR-12, US-QG-07, #1243)

- **Indexes added:** `ai_log_connection_day` (`ai_log (account_id, connection_id, created_at)`, migration `0099`, module `ai`) for the daily AI limit (`AiLogPostgres.countSince`, every AI call); `review_case_open` (`(created_at, id)` where the status is `proposal` or `ai_unreviewed`) and `review_case_curated_species` (`(created_at desc, id)` where the status is `curated` and the object kind `species`) for the two lists of `ReviewPostgres.listForReview`, and `species_latin_name` (`species (latin_name)`) for the ordered species search, all in migration `0100` (module `catalog`); `taxon_attribute_field` (`(field, latin_name)`) for `TaxonAttributesPostgres.speciesWith`, migration `0101` (module `pokedex`). The module gate (AB-14) allows one module per migration file, which is why the indexes come in three files.
- **Measured on synthetic data** (PostgreSQL 18, 20 000 species with their review cases, 328 500 AI log rows, 25 000 taxon attributes, 65 000 jobs, the queries run as `pflanzendex_app` where row security applies, median of five runs): the batch list of curated species 53 ms to 0.2 ms, the ordered search 424 ms to 4 ms, the open-case list 2.1 ms to 0.9 ms, the taxon list 4.3 ms to 0.4 ms; the daily count of a busy account (ten connections) 458 buffers to 5. The plans of the other queries on these tables do not change (the species lists of the fill and gap stores and the Wikidata claims still sort after a sequential scan).
- **Query change:** the expiry UPDATE of `TasksPostgres.create` compares `md5(reference) = md5($2)`, the expression of the unique index `ai_task_active`, so the planner looks up the one row instead of filtering the account's tasks of the type. The lookup and the stored semantics are unchanged: the index already treats two references with the same MD5 as the same task.
- **Not added:** an index on the expiry of queued jobs (`job`, the sweep every 5 s in `JobsPostgres.claim`). The partial index `job_due` already limits the sweep to queued jobs; at 200 queued jobs the sweep takes about the same time with or without an index. The index only halves the scan with a backlog of 50 000 queued jobs, where the update of the due rows takes most of the time.
- **Locks:** the runner applies each migration file in one transaction, so `create index concurrently` cannot be used; the migrations use plain `create index`, which blocks writes to the table for the build (milliseconds on the synthetic data). `ai_log` is the largest table and grows without purge: check its size before a deploy that carries `0099`. A concurrent build would need a change of the runner (open).
- **Open (not done):** `location_zone` (index on `location (light_zone_id)`, superseded by `location_light_zone (account_id, light_zone_id)`) and `ai_log_connection (account_id, connection_id)` (a prefix of `ai_log_connection_day`). Drop each one only after its `idx_scan` is 0 in production.

## Sign-in (US-ACC-01, E-03)

- **Local auth server:** `make auth-up` starts Keycloak 26.8 (port 18081, realm `pflanzendex`, imported from `app/config/dev/keycloak/pflanzendex-realm.json`) and a mail catcher (Mailpit, http://localhost:18025). The containers are shared by every checkout, so `make auth-up`, `auth-down` and `stop` always use the main checkout's `app/config/dev/compose.yaml` and `app/config/dev/.env` (not in the repo), also from a worktree (`app/tools/keycloak/auth-up.mjs`, issue 1187). Only the main checkout creates the `.env` with a random admin password; a worktree without it, or a running container with another password, is refused instead of recreated. Tools that need the password read it there (`app/tools/keycloak/dev-env.mjs`). `make auth-down` removes both containers, including their data.
- **Usernames and test accounts (dev realm only, US-DEV-01):** sign in with a username or the email (registration asks for a username). The import creates the accounts `test`, `test2` and `test3` (emails `<name>@example.test`, verified, password `testtest12`). Keycloak imports the realm only when it does not exist yet, so an already running auth server keeps its old data: `make auth-down && make auth-up` recreates the realm with the accounts. `make start` runs everything below in one go (auth server, database, API and web) and prints these accounts; `make stop` stops the containers again.
- **Theme and scope:** the realm uses the login theme `pflanzendex` (`app/config/dev/keycloak-theme/`, mounted by `app/config/dev/compose.yaml`; #205, US-QS-14). It is the frame of the welcome page too (`web/src/account/views/auth-frame/`, same drawing, value lines and German texts): the template `login/template.ftl` (wordmark, drawing, value lines), the colours of ADR 0017 copied into `login/resources/css/pflanzendex.css`, Figtree self-hosted in `login/resources/fonts/`, the German "du" texts in `login/messages/messages_de.properties`, German only (`locales=de`, no language dropdown), the field template `field.ftl` (`aria-invalid` only on an error). Guards: `app/tools/keycloak/theme.test.mjs` (no external request, tokens equal to the web app, contrast, texts, the drawing equal to the welcome page). To look at the theme without the shared auth server, run a second Keycloak 26.8.1 on another port with the theme mounted (`-v <theme>:/opt/keycloak/themes/pflanzendex:ro`, `start-dev --import-realm`); the protocol of US-QS-14 describes the setup. The web client has `fullScopeAllowed: false`; the audience mapper keeps the API token valid. Access tokens live 5 minutes (ADR 0009).
- **Redirect ports:** the realm allows port 5173. A worktree runs on its own port: `cd app && node tools/keycloak/web-port.mjs` adds `PFLANZENDEX_DEV_WEB_PORT` of `.env.worktree` (or the ports given as arguments) to the web client through the admin API; run it after `make auth-up` (idempotent; #202). `make dev` reads `.env.worktree` itself (`app/tools/workflow/worktree/dev-servers.mjs`, #904): the API on its port, Vite with `--port` and `--strictPort`, the API origin and the worktree's test database, nothing to set by hand. Details: `docs/guides/operations/parallel-work.md`. The three seeded users have first and last names, so the first sign-in shows no profile form (the realm must be imported again, `make auth-down` then `make auth-up`).
- **Flow:** the web app redirects to Keycloak with the OIDC authorization code flow and PKCE (sign-in and registration happen there, in German). Keycloak first requires email confirmation, then setting a password (policy: at least 10 characters in the development realm; deployments require 12 and neither the username nor the email address, see `staging-deploy-and-backup.md`). Passwords never reach us (FR-ACC-03).
- **API:** `Authorization: Bearer <access token>`; signature (JWKS), issuer and audience `pflanzendex-api` are verified. Every request sets the account via `withAccount`. `GET /account` returns the caller's own account data, with `keyboardShortcuts` (US-QS-11, the mode of the shortcuts). Environment: `OIDC_ISSUER`, `OIDC_AUDIENCE`, `DATABASE_URL`, `WEB_ORIGIN`.
- **Account creation:** `findOrCreateAccount` (db) is the dedicated path for the first sign-in: the `anmeldung_*` policies on `account` show and allow only the row of the verified subject (`app.subject`). No BYPASSRLS.
- **Web:** `VITE_OIDC_AUTHORITY`, `VITE_OIDC_CLIENT_ID` and `VITE_API_URL` override the defaults. "Sign out on all devices" calls the Keycloak account API (`DELETE /account/sessions`).
- **Tests without Keycloak:** token, middleware and UI tests run without the auth server (locally generated keys). The flow against Keycloak was checked manually: `docs/records/test-logs/acc-01.md`.

## Reminder delivery by Web Push (US-MON-01, #941)

- **Adapter:** `WebPushReminderChannel` (`api/src/monitoring/push/web-push-channel.ts`) implements the port `ReminderChannel` of the daily job `monitoring.send_reminders`. It sends one push per subscription of the account (`delivery_channel`) with `webPushSender` (`push/web-push-config.ts`): the library `web-push` encrypts the payload (RFC 8291, `aes128gcm`) and signs with VAPID (RFC 8292); the request goes straight to the subscription's endpoint with `fetch` (`TTL` one day, `Urgency: normal`, 10 s timeout). No FCM, no push vendor (ADR 0015).
- **Outcomes:** 2xx = delivered; 404 or 410 = the subscription is dead and removed (`ChannelStore.remove`); anything else or a network error = failed. One delivered subscription is enough; otherwise the send throws, the job retries and the third failure leaves the reminder `failed` (FR-MON-08). Logs and errors name only the host of an endpoint, never its path.
- **Payload:** `pushPayload` builds `{ title, body, url, items, more }` in the order of the bundle and cuts `items` to `PUSH_PAYLOAD_LIMIT` (3000 bytes, starting value); `more` counts the rest, the inbox keeps everything.
- **Configuration:** `reminderChannelFromEnv` (`api/src/monitoring/runtime.ts`, used in `main.ts`): `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`. None set: `StubReminderChannel` (sends nothing, logs). Partly set or invalid keys: the stub stays and the API logs what is missing or invalid at start. Keys: `npx web-push generate-vapid-keys`.
- **Limits:** no route for the public key, no subscribe flow and no service worker in the web app yet (follow-ups of US-MON-01), so no browser registers a subscription; no email channel.

## Access by invitation only (US-ACC-05)

- **Data:** migration 0018 (`-- module: account`): `invitation` (SHA-256 hash of the code, expiry as `timestamptz`, `redeemed_at`), `access_setting` (one row, `invitation_only`, default off) and `account_data.last_active_at`. Neither new table has an `account_id`: both are justified entries in `WITHOUT_ACCOUNT_ID`, have row security enabled without any policy (`ENABLE` only, not `FORCE`: the `security definer` functions run as the table owner and must keep working if the owner is not a superuser), the application role has no right on them (like `account_role`) and reaches them only through `security definer` functions that check the operator role again (`is_operator()`): `create_invitation`, `list_invitations`, `set_invitation_only`, `operator_overview`; `redeem_invitation` (needs the verified subject of the registration path) and `invitation_required` need no role.
- **Monthly operating cost (migration 0021):** `operator_cost` (one row, like `access_setting`: `amount_cents`, `currency`, `month`, all null until the operator enters a figure) is another justified entry in `WITHOUT_ACCOUNT_ID` with row security on and no policy; the operator reaches it only through `set_operator_cost` and `operator_cost`, which check `is_operator()` again and refuse a month after the current one (UTC). `operator_overview` is unchanged, so the previous app version keeps working; core derives the cost per user (`costPerUser`, rounded half up to whole cents, unknown without a figure or without active accounts).
- **Codes:** `newInvitationCode` (`core/src/account/invitation-code.ts`) turns 15 bytes from the injected CSPRNG (`crypto.randomBytes` in the API) into 24 Crockford base32 characters (120 bits), shown as six groups of four. The code is returned once by `invitation.create`; only its hash is stored, so a leaked database holds no codes. Lookup is an equality match on the hash (no secret-dependent comparison in application code). Typed codes are normalized by a linear scan (case, spaces, hyphens, `O`/`I`/`L`), never by a pattern on user input. `invitation.create` is marked `secret` (`Operation.secret` in `core/src/kernel/operation.ts`): its answer is never written to the `idempotency` table and the key is released after the run, so a repeat with the same `Idempotency-Key` creates another single-use code instead of replaying the old one (tested by querying the table). Calls that are still running stay guarded by `idempotency.in_progress`.
- **Single use:** `redeem_invitation` is one conditional update (`redeemed_at is null and expires_at > now()`); concurrent redeems wait for the row lock and then find it used (tested with 20 parallel registrations of one code: exactly one account). The account is created in the same transaction (`AccessPostgres.register`); a subject that already has an account (or gets one from a concurrent request) rolls everything back and keeps the code unused. Expiry is an UTC instant, compared with the database clock.
- **Registration gate:** `authentication` calls `admitAccount`: a known subject always gets its account; an unknown one only while `invitation_only` is off. Otherwise every protected route answers 403 `invitation.required` and creates nothing. `POST /registration/invitation` (`{ code }`, bearer token, no account needed) registers the subject: 200 `{ registered }` or 403 `invitation.invalid`, the same answer for an unknown, used, expired or malformed code (no oracle). This one write has no `Idempotency-Key` (there is no account yet); it is naturally repeatable. It has a limit of its own on top of the general write limit below (`REDEEM_LIMIT`, issue 305; starting values, assumption): 5 attempts per subject and 20 per address and minute. `createApp({ invitationOnly })` forces the mode per app instance (tests only: they must not flip the shared setting).
- **Write limit (TE-03, #762):** every `POST`, `PUT`, `PATCH` and `DELETE` counts against a fixed window per client: 120 writes per minute (`WRITE_LIMIT` in `api/src/kernel/write-limit.ts`, starting value, assumption). The client is the `sub` of the bearer token (read without verifying, only to pick the counter; authentication still checks the token), otherwise the first address of `X-Forwarded-For`. Over the limit: 429 `request.rate_limited` with `Retry-After` in seconds; nothing is written. Reads, preflights and `/health` are not counted. The counters live in the memory of the API process (one process per installation, E-01) and are lost on restart. The server (`main.ts`) passes it to `createApp({ writeLimit })`; without that option nothing is limited, because tests and the demo seed write through the app in process. **Redeem limit (US-ACC-05, issue 305):** `POST /registration/invitation` counts its attempts per subject and per address, fixed windows of one minute, the same memory and bound as the write limit: 5 per subject and 20 per address (`REDEEM_LIMIT` in the same file; starting values, assumption; `createApp({ redeemLimit })`, `main.ts` passes it; without the option nothing is limited). It is checked after the token is verified, the subject first; a refused attempt counts nowhere and answers 429 `request.rate_limited` with `Retry-After` before the database is asked. The address is the first `X-Forwarded-For` value, the same as above: it is only as good as the proxy in front of the API, and behind a proxy that does not set the header all clients share one address.
- **Operator area (operator role only, not reviewers):** `GET /operator/overview` (`accounts`, `activeAccounts` (opened the app within `activeWindowDays` = 30, assumption), `costPerUser` (always `null` = "unbekannt", there is no cost measurement, P-08), `invitationOnly`, `invitations` with state `open|redeemed|expired`, never a code or a person), `PUT /operator/registration` (`{ invitationOnly }`, `Idempotency-Key`, operation `registration.set_mode`), `POST /operator/invitations` (`{ validForDays }` 1 to 30, default 7, `Idempotency-Key`, operation `invitation.create`, 201 with the code once). `GET /account` has a new hint `operator` (the UI shows the tab "Betreiber"; the operations check the role again). `GET /account` refreshes `last_active_at` when it is null or older than an hour, so at most one such write per account and hour (issue 305).
- **No content for the operator (P-05):** the overview functions return counts only; no row rule is opened by the operator role (tested by scanning the policies), and the operator account reads no foreign row of any tenant table (tested as a sweep).
- **Web:** after sign-in, a 403 `invitation.required` shows the form "Einladungscode" (`InvitationPage`); the tab "Betreiber" (`OperatorPage`, `account/operator`) shows one row per topic with its current value (Zahlen, Einstieg, Monatliche Kosten, Registrierung, Einladungscodes); each row opens its topic as a layer (`LayerSheet`, `?sheet=` with the topic id (zahlen, einstieg, kosten, registrierung, einladungscodes), US-QS-15): the counts, the introduction figures, the cost form, the mode with its one action, and the codes (the form, the new code once, the invitation list in pages of five, `?lpage=n`, `INVITATIONS_PAGE_SIZE`). The write hook is `operator-page/operator-actions.ts`; each write shows its outcome in the layer it came from.
- **Limits:** the operator role is assigned by hand (`account_role`), as before. Closing self-registration at the sign-in service (Keycloak) is a realm setting outside the app.

## Species catalog (US-BES-01)

- **Data:** migration 0005: `art` (profile per DM-BES-01) and `species_name` (Latin, German and English name, synonyms, each with a normalized search key). Every species has exactly one review process (composite foreign key `(object_kind, id)`, `on delete restrict`: deleting an account never takes a catalog species with it). The catalog has no `account_id`: both tables are justified entries in `WITHOUT_ACCOUNT_ID` and also listed in `CATALOG_TABLES`, for which the generic schema test demands enforced row rules.
- **Visibility (FR-BES-11):** everyone sees a species when its process is `curated` or `reviewed`, otherwise only its creator (also `rejected`). `species_status()` (`security definer`) decides for the other modules; the species rows use the copy below. Its reason: `review_case` hides other accounts processes; for that, only the owner role may read approved processes (policy `catalog_approved`). `ai_unreviewed` stays private unless an operator batch creates it. The application has only `select` and `insert` on `art` (insert only with an own process); there is no update or delete. Reviewers do not see private proposals yet (that view belongs to BES-10).
- **Visibility on the species row (NFR-12, #1235, migration 0102):** `species` carries `review_status` and `review_account`, the status and creator of its review case. Trigger `species_review_copy` (before insert of a species) and trigger `review_case_species_sync` (after every insert, update or delete of a review case) keep them current; both are `security definer` and registered in the audit. The review case stays the source of truth. The row rules of `species` and `species_name` (`visible`, `reviewer_reads`) are plain column predicates over these columns, so a catalog query calls no function per row. The triggers are `enable always`, so seeds and fixtures that write with `session_replication_role = replica` keep the copy too.
- **Search (NFR-12):** `GET /species?q=` reads `species_name` first (`searchQuery` in `catalog/species/species-read.ts`, db package) and computes the columns of at most 51 species: the cap of 50 (FR-BES-24, `SEARCH_LIMIT`) and one row more, which tells `more`. Decided (owner, 2026-11-04): no trigram index, because `like '%term%'` cannot use an index for the application role while `species_name` is under row security (`like` is not leakproof; plan measured for #1235), so the index would only cost writes. A table of approved names without row rules is a possible follow-up.
- **Scaling gate (NFR-12, US-QG-07, #1249):** `src/species-catalog-scaling.test.ts` (db package) seeds 100 and 2,000 species (the extra ones invisible to the viewer) and runs the species list, the search and the Pokedex facts (`APPROVED_FACTS`) as `pflanzendex_app`. It fails when a read costs more than twice as many function calls (`pg_stat_user_functions`, `track_functions = all`) at 2,000 species, or returns other rows. Buffer hits and subplan loops are not the metric (they grow with the sequential scan and the accepted name scan); the self-test applies the pre-0102 policies in a rolled-back transaction and shows the search failing. Numbers: `docs/records/test-logs/nfr-12.md`, section 13.
- **Operation:** `art.propose` (`core/catalog/art`) creates species, names and the `proposal` process in one transaction. Duplicates (same normalized Latin name or synonym among the visible species) return `art.duplicate` with the existing species and write nothing. Private proposals of different accounts are not duplicates (the error would reveal foreign data); BES-10 merges them.
- **Required fields of a proposal (assumption):** Latin name, difficulty 1-3, default level 2-4, light need (lux), growth measure, etiolation signs, success criteria. Everything else is optional and shown as "unbekannt" when missing (P-08); the dormancy period only counts as a pair. A source for light need and dormancy is required only for approval (FR-BES-14).
- **API:** `GET /species?q=` answers `{ species, more }` (partial word, accent- and case-insensitive, names the name it matched). `species` holds at most 50 hits (FR-BES-24, a starting value, assumption); `more` is `true` when more species the account may see match (a foreign proposal never counts, P-05). `speciesSearch` in core returns the same `SpeciesSearch`. Duplicate hints (`speciesExisting`, and the `similar` list of the review list through `similarTo`) and name references (`resolveSpecies`, `get_species`, the species filters) also find an exact name beyond the cap: the store method `exact(userId, norm)` (`speciesExact` in core) returns the visible species with a Latin, German, English or synonym name equal to the term, without the cap, and it is read only when `more` is true (`withExactBeyondCap`; the AI module restates that rule because it may not import the catalog module). `GET /species/:id` (foreign or unknown species: 404), `POST /species` (`Idempotency-Key`).
- **Limits:** the catalog stays empty until the catalog job (POK-03) or operator batches fill it. The hand-over to the AI client (US-KI-08) is missing. "Diese Art wählen" hands the species to the Bestand tab (US-BES-02, below). Image, traits, versions (FR-BES-12) and editing an own proposal do not exist yet. ## Specimens (US-BES-02)

- **Data:** migration 0007 (`-- module: collection`): table `specimen` with `account_id` and a row rule (generic tenant test plus fixture `FIXTURES_COLLECTION`), the name unique per account (case-insensitive), `caught_at` as `date` (a local calendar day, read back as text, never as a `Date`), `status` (`plant`, `cutting`, `archived`), `location_id` empty = "unbekannt". Migration 0006 (`-- module: light`) only adds `unique (account_id, id)` on `location`, the target of the composite foreign key `specimen_location (account_id, location_id)` (AB-10, AB-14: a migration touches only the tables of its module, so the licht change is its own file).
- **Art reference (AB-10, global reference table):** `specimen.species_id` has the plain foreign key `specimen_species` to `art(id)` with `on delete restrict` (migration 0008). `art` has no `account_id`, so it is registered in `GLOBAL_REFERENCE_TABLES` (`modules.config.mjs`, with owner and reason); the gate allows such a key only from a module that may depend on the owner, only to `(id)` and only with `on delete restrict`. The database refuses an unknown species and the deletion of a species in use; the operation still reads the species through the catalog (`SpeciesSource`) under the caller's account, so private proposals of other accounts stay `art.not_found`. The application role still cannot delete species. Tests needing a species use `createFixtureSpeciesAt` (`db/src/fixtures.ts`).
- **Operation:** `specimen.create` (`core/src/collection`). Only the species is required (plus the time zone of the profile, US-ACC-02; the device's zone only as fallback). Name by DM-BES-03 before saving: species name (German, else Latin; assumption), with a marker `Species – marker`. A taken name writes nothing and returns `specimen.name_taken` with the existing specimens of the species (the database unique index decides, no pre-check race). `Gefangen_Am` is `localToday(uhr, timeZone)` (`kernel/input/date.ts`, NFR-08). The time zone comes with the request: the web app sends the one of the profile (US-ACC-02), the device's zone only as fallback while none is chosen.
- **target location (limit):** the port `TargetLocationSource` (defined in `collection`, to be implemented by `care`) is asked for the location of the species for today. Without phase logic (PHA) and care profile (BES-09) nothing implements it: `NO_TARGET_LOCATION` answers "unbekannt" and the location stays empty unless the keeper chooses one of their own. Nothing is invented (P-08). A chosen location wins over the port.
- **measurement series and treatment list:** returned as empty derived lists (`measurements: []`, `treatments: []`), no columns, no tables; WAC and BEH bring their own.
- **API:** `GET /specimens`, `GET /specimens/:id` (foreign or unknown: 404 `specimen.not_found`), `POST /specimens` (`Idempotency-Key`; body `speciesId`, `timeZone`, optional `marker`, `locationId`). Errors: `specimen.name_taken` 409, `art.not_found` and `location.not_found` 404.
- **Web:** tab "Bestand"; "Diese Art wählen" in the catalog opens the form for that species (the app wires `catalog` and `collection`, the modules do not know each other).
- **Limits:** no editing of location, status or other fields and no deleting (renaming by marker: US-BES-03; archiving: US-BES-07); addition, zone override, provenance and sharing fields of DM-BES-02 are missing; no specimen hints yet (BES-08).

## CSV import of plants (US-BES-18, slice 2 of issue 1330)

- **State:** core, API and web are built (slices 2 and 3). The page `/collection/import` offers the template, the preview with the keeper's fixes and the result (see the last bullet of this section).
- **Core:** `core/src/collection/bulk/`. `parseImportCsv` (`csv/`) reads the text: UTF-8 with or without a byte order mark, separator from the header line (comma or semicolon), RFC 4180 quotes, columns by normalized header (`Art`, `Spitzname`, `Standort`, `Kaufdatum`, `Notizen`, or `species name`, `nickname`, `location`, `purchase date`, `notes`), dates `YYYY-MM-DD` or `DD.MM.YYYY`. Limits `IMPORT_LIMITS` (500 rows, 1 MB in UTF-8 bytes; starting values, assumption).
- **Operations:** `specimen.import_preview` (`specimenImportPreview`, `preview/`) is a read and writes nothing. Input `csv`, `timeZone`, `markers` (answers for existing specimens, optional), `overrides` (the keeper's fixes, optional, at most one per line and at most 500, keyed by the line of the file: `{ line, speciesId?, marker?, skip? }`). Output: `rows` (line, `state` ready / flagged / already_there / skipped, `species` with `id` and `candidates`, the values, `specimenName`, `location` with `isNew`, `reasons`), `counts` (`ready`, `flagged`, `alreadyThere`, `skipped`), `newLocations`, `markers` (the existing specimens that still need a marker). A fix of `speciesId` replaces the name match of its row and is checked through the port `ImportSpeciesSource.byId` (the visible species, `speciesLoad`); a foreign or unknown ID leaves the row flagged with `import.species_not_found`. A fix of `marker` replaces the nickname (an empty text means none) and is judged like a nickname. `skip: true` leaves the row out of the plan: it counts toward no marker and no new location and is answered as `skipped`. A line the file does not have is refused as `input.invalid` (field `overrides`). `specimen.import` (`specimenImport`, `confirm/`) is the one guarded write (`Idempotency-Key`). Input `timeZone`, `rows` (at most 500: `line`, `speciesId`, `marker`, `locationId` or `newLocation`, `catchDate`, `notes`), `markers`. Output `created`, `skipped`, `refused` (with the code), `locationsCreated`, `unusedMarkers`. Every row runs through the validating `specimen.create`, and every new location through the validating operation of the light module (indoor, without a zone) (P-03); a refused row does not stop the others.
- **Species:** a row is ready only on an exact name or synonym (case and accents ignored). The catalog's lookup (`exactSpecies`, uncapped) finds the candidates; each hit must then equal the cell with `normalizeName` (so `Fusspflanze` is not `Fußpflanze`). Partial, several or no matches are flags with candidates (at most 20) or none. The import never creates a species. The API adapter is `importSpeciesFor` (`api/src/collection/bulk/import-routes.ts`) over `collectionReadSourceFor`, the reads of the app's search (P-04).
- **Markers:** `preview/rules/markers.ts` judges the whole file for one species in file order, as `planMarkers` judges one create. The rule of three: from the third active specimen on every row needs a marker, and the row that makes the third needs the answers of the existing unmarked specimens; the answers go to that row in `confirm`. `markers.test.ts` checks that every row the preview does not flag is created, over every file shape up to three rows.
- **Already there:** a row whose specimen name (DM-BES-03) exists for its species, archived ones included, is `already_there` on the preview and `skipped` on the confirm, before the create's marker check; a repeat of the import creates nothing twice. A file's own repeat (same species, same marker, case-insensitive, or both empty) is `import.duplicate_row`.
- **Routes:** `POST /specimens/import/preview` (a read: no `Idempotency-Key`; takes the `overrides`; a body above 2 MiB + 64 KiB answers `import.too_large` 413) and `POST /specimens/import` (`Idempotency-Key`; a body above 8 MiB answers `input.invalid` 400). Both are under `/specimens/*` (sign-in guard). Both refuse with `onboarding.keeper_off` (409) while the keeper switch `csv_import` is off, and nothing is written, as the leaf log does (P-12).
- **Errors:** new codes `import.file_unreadable` (400), `import.no_species_column` (400), `import.column_repeated` (400), `import.too_large` (413), and the row reasons `import.species_missing`, `import.species_not_found`, `import.species_candidates`, `import.duplicate_row` (flags in a successful answer, not failures). Reused: `specimen.caught_in_future`, `specimen.marker_required`, `specimen.marker_taken`, `specimen.markers_missing`, `specimen.name_taken`, `input.invalid` (dates before 1900 or impossible, long marker, location or notes). German texts in `IMPORT_ERROR_TEXTS` (`kernel/error-texts/catalog.ts`).
- **Keeper switch:** `csv_import` (BES, rule `always`: open from the start, also without plants, US-ONB-04). No operator feature and no web flag.
- **AI:** `csv_import` and `private_notes` (the notes of a specimen) are class `never` in `AI_OPERATION_CLASSES` (FR-KI-22); no MCP tool reaches the import.
- **Web (slice 3):** the page `/collection/import` (`PrintLabelsPage`-style: `ImportPage` in `web/src/collection/other-pages/import-page/`, lazy through `collection/index.ts`, the route in `app/routes.tsx`, the address `IMPORT_PATH` in `shared/patterns/navigation/navigation/navigation.tsx`). Switched off ("csv_import"), the page redirects to the collection. Three steps in component state (`import-flow.ts`, the actions in `import-controller.ts`, the HTTP calls and the template in `import-api.ts`): choose (a `.csv` file read with `File.text()`, a file over 1 MB refused in the browser with `import.too_large`'s text, the template `pflanzen-vorlage.csv` as a Blob with its one header line), preview (counts, new locations, the marker answers, the rows paged with `Pager fit`, every fix sends the file again with `overrides` and `markers`), result (`POST /specimens/import` with the `Idempotency-Key` of `createWrite`, only the ready rows of the last preview). Reasons show as German text by their code (`errorText`). The entry "Aus Datei importieren" (`views/import-entry/`) sits on the species step of "Pflanze anlegen" and of the first-plant guide (the wizard's `entry` prop), hidden while the switch is off. The texts are in `import-page.de.json`.
- **Decision (noted):** the preview takes the marker answers as an optional input. Without it the preview could never clear a `specimen.markers_missing` flag, because the answers can only come from the keeper.

## Tell several specimens of a species apart (US-BES-03)

- **Data:** migration 0013 (`-- module: collection`): unique index `specimen_marker_per_species (account_id, species_id, lower(marker))` for rows with a marker; archived specimens count, their marker stays taken like their name (US-BES-07). The name was unique per account already, so no existing data can violate the index.
- **Naming rule (DM-BES-03), `core/src/collection/shared/markers.ts`:** the 1st specimen is plain; a further one needs a marker (`specimen.marker_required` 409, with name and existing specimens; before US-BES-03 this case was `specimen.name_taken`). The marker is unique per species, case-insensitive (`specimen.marker_taken` 409). From the 3rd **active** specimen on, every active specimen has a marker: `specimen.create` returns `specimen.markers_missing` 409 (data `missing: [{id, name}]`, nothing written) until the request carries `markers: [{specimenId, marker}]` for each of them; those renames and the insert run in one transaction (`SpecimenStore.create(…, assignments)`). An answer for a specimen that is not missing (also a foreign one) is 404 `specimen.not_found`. Archived specimens do not count and are never renamed (their name and marker stay taken).
- **Rename:** operation `specimen.mark` (`POST /specimens/:id/marker`, `Idempotency-Key`, body `marker`): sets marker and name (`Species – marker`) in one statement. The ID, location, date and status stay, so renaming changes no references (the name is display text). Empty marker is 400 `input.invalid`, a taken one `specimen.marker_taken`, an archived specimen `specimen.archived` 409, a foreign or unknown one 404 (P-04). The name is derived from the species' current display name; the marker of the specimen itself may change case. Changing the location of an existing specimen is **not** part of this story (follow-up, PHA-03).
- **Web:** the form preselects the marker "Klammer" from the 2nd specimen on (only a preset, not applied if a specimen carries it already) and asks for the markers existing specimens miss before it sends anything; the card has "Kennzeichen" to give or change a marker (form with name preview; message "… heißt jetzt …", errors stay visible). `SpecimenCard` carries `speciesId` and `marker` for this.
- **Limits:** restoring an archived specimen can leave three active specimens with one unmarked (the rule is checked when creating and renaming, not when restoring); the preset "Klammer" is a UI default, the API requires an explicit marker.

## Create a cutting and pot it (US-BES-04)

- **Data:** no migration. `status` already knew `cutting` (0007, renamed in 0012). Cutting light is **derived** (P-01): the lowest zone of the account (`cuttingLight` in `core/src/collection/placement/cutting-light.ts`, the same rule as the count in `zoneDistribution`), so there is no stored zone override to delete when potting.
- **Operations:** `specimen.create` takes an optional `status` (`plant` default, or `cutting`; anything else is 400 `input.invalid`). A cutting without a chosen location gets the location of the growth phase from the port `TargetLocationSource.growthLocation` (also in the dormancy phase), a plant the target location as before; without an answer the location stays "unknown" (P-08). `specimen.repot` (input `specimenId`, optional `timeZone` and `date`) turns a cutting into a plant in one statement; the repot day is the chosen local day `date` (`YYYY-MM-DD`, from 1900 on; a later day is 400 `specimen.repotted_in_future` on the field `date`; a day without `timeZone` is 400 `input.invalid`, since it cannot be checked; a day before the catch date is 400 `specimen.repotted_before_caught` on the field `date` and nothing is written, a cutting without a catch date accepts any past day, P-08), else today in the keeper's zone. A plant is repotted too (US-BES-19): its status and its repot day (potting out) stay, the repot is recorded in `repot`, and a plant without a day is 400 `input.invalid` on `timeZone`; an archived specimen is 409 `specimen.archived` (nothing is written), a foreign or unknown one is 404 `specimen.not_found` (P-04). Every repot clears the open repot observations of the specimen on its day (the repot itself is one transaction, `repotSpecimen` in `db/src/collection/specimen/specimen-repot.ts`).
- **API:** `POST /specimens` accepts `status`; `POST /specimens/:id/repot` (`Idempotency-Key`; body `timeZone` and optional `date`, an empty body records today; a plant needs `timeZone`, US-BES-19). - **US-BES-19 repot history and observations (migration `0112`, module `collection`, DM-BES-09):** table `repot` (`repotted_on`, one row per repot day; backfilled from `specimen.repotted_at`, composite foreign key to `specimen`, tenant protection with a fixture) and table `repot_sign` (`sign` `roots_out | dries_fast | tips_over`, `ticked_on`, `cleared_on`; one open observation per sign and specimen, `cleared_on` never before `ticked_on`). The keeper switch is `REPOT_PLANNER_KEEPER_SWITCH`.
- **US-BES-19 pots and placements (migrations `0111` and `0113`, module `equipment`, DM-EQU-05, DM-EQU-06):** `equipment` has the pot fields `diameter_cm`, `height_cm` (numeric, 1 to 300, one decimal), `material` (1 to 60 characters) and `drainage` (boolean), all nullable (unknown, P-08) and allowed for type `Pot` only (check `equipment_pot_fields_pots_only`). The adapters are `PotPlacementPostgres` (`place`, `currentPot`, `freePots`) and `PotRepotPostgres` (`run`, the repot with a pot as one transaction, the handover pattern, `db/src/equipment/pot-repot-unit.ts`). Refusals: `specimen.not_found` (also for a foreign plant, P-04), `specimen.archived`, `equipment.not_a_plant` (a cutting is potted out first), `equipment.pot_not_found` (404; foreign, defective, retired or not a pot), `equipment.pot_taken` (409), `onboarding.keeper_off` while the keeper switch `equipment` is off (`EQUIPMENT_KEEPER_SWITCH`; taking a plant out stays possible).
- **API US-BES-19 pots:** `POST /specimens/:id/repot` (`Idempotency-Key`; body `timeZone`, optional `date` and `potId`; 200 with the plant (`id`, `status`, `repottedAt`) and `pot` (the placement, or `null`); the write is `specimen.repot_with_pot`, the composition in `specimenRepotWithPotOf` in `api/src/collection/specimens/specimens-routes.ts`). `POST /specimens/:id/pot` (`Idempotency-Key`; body `potId` (`null` takes out), `timeZone`, optional `date`; operation `equipment.place_pot`, route file `api/src/collection/repot/repot-plan-routes.ts`).
- **API US-BES-19 repot plan:** `GET /specimens/:id/repot-plan?timeZone=` (route file `api/src/collection/repot/repot-plan-routes.ts`) answers `{ specimenId, status, hidden, equipmentOff, hints, lastRepot, phase, seasonAdvice, currentPot, freePots }`, derived on every request by the pure `repotPlan` (`core/src/collection/repot-plan/plan.ts`, plain inputs; the phase from `carePhasesOf`, the placements from `PotPlacementPostgres`, the observations from `RepotPostgres`). A foreign or unknown plant is 404 (P-04), a missing or invalid `timeZone` 400, a cutting or archived plant gets no hint.
- **Keeper switch repot_planner (US-ONB-09, P-12):** `REPOT_PLANNER_KEEPER_SWITCH` in `KEEPER_SWITCH_IDS` with an unlock function `repot_planner` (rule `always`, destination `collection`, like `csv_import`); its German name, purpose, empty-state sentence and address are in the web tables (`web/src/app/flows/unlock/model/unlock-texts.ts`, `function-purposes.ts`), provisional until the owner confirms them.
- **API US-BES-19:** `POST /specimens/:id/repot-signs` (`Idempotency-Key`; body `sign`, `ticked` (boolean, `true` ticks, `false` clears), `timeZone`; 200 with `{ specimenId, signs }`; 400 `input.invalid`, route file `api/src/collection/repot/repot-routes.ts`, mounted in `specimenRoutes`).

## Care phases (US-PHA-01)

Only specimens with status `plant` whose species has a dormancy period are listed (cuttings and archived ones are not).
- **API:** `GET /carePhases?timeZone=<IANA name>` returns `{ phasen: [{ specimenId, name, speciesId, phase, locationId, targetLocationId }] }` sorted by name; a missing or invalid time zone is 400 `input.invalid` with the field `timeZone`. The time zone comes with the request: the web app sends the one of the profile (US-ACC-02), the device's zone only as fallback while none is chosen.
- **Web:** tab "care phases", with an empty state that says what to do next (P-09).
- **Limits:** the target location per phase belongs to the keeper's care profile (BES-09, missing), so `targetLocationId` is always `null` ("unbekannt", P-08); `TargetLocationSource` (FR-PHA-05) is not implemented yet. A dormancy period on the specimen itself (override) does not exist. The E2E flow with an specimen waits for a fillable species catalog; E2E covers the empty state.

## Specimen cards (US-BES-06)

- **What:** `GET /specimens/cards?timeZone=Europe/Berlin` returns one derived card per own specimen (no table, no migration): name, species name, status, location, light zone with its source `lightZoneSource` (the effective zone the distribution counts too, FR-LIC-02: `cutting` light for a cutting, else the zone of the `location`, else my care-`profile` override, else the zone derived from the `species` lux need; both `null` when unknown; a zone field on the specimen itself comes with BES-04), last measurement, photo, and the earliest open treatment with "+N weitere". A missing or unknown time zone is `input.invalid` (400); "today" is the local date in that zone (NFR-08). The route sits before `/specimens/:id`.
- **Ports (module `collection`, registered in `modules.config.mjs`):** `MeasurementSource` (last measurement and youngest photo per specimen) and `TreatmentSource` (open treatments, `care`/BEH). Both are asked once for all own specimen ids, never for foreign ones. `care` implements `MeasurementSource` (`measurementSource` in core, `MeasurementStore.lastFor` in db, wired in `createApp` via `measurementSourceFor`): the cards show the last measurement and the most recent photo (`MeasurementStore.lastPhotoFor`; `url` is the private API path `/specimens/:id/measurements/:mid/photo?v=<version>`, which the web fetches with the token, US-WAC-05; the version changes with every replacement, NFR-12, see Photo below). `care` also implements `TreatmentSource` (`treatmentSource` in core, `TreatmentsPostgres.open` in db, wired in `createApp` via `treatmentSourceFor`, US-BEH-01): cards show the next open treatment and "+N more". `NO_TREATMENTS` stays the null implementation for `specimenRoutes` used without `care` (tests). `createApp` takes `measurements` and `treatments` options to replace them (tests).
- **Unknown stays unknown (P-08):** a species the account cannot see, a location without zone or a missing location is `null` and shown as "unbekannt". Etiolated growth ("Vergeilt/dünn") is shown as a warning, never as success.
- **Web:** tab "Bestand" shows the cards in a grid (`repeat(auto-fill, minmax(min(100%, 16rem), 1fr))`: one column on narrow phones, more when there is room); the note of the last measurement is a native `<details>`; the photo is a link that opens it large.
- **Limits:** photo, measurement and treatment data appear only once WAC and BEH implement the ports (the card logic is tested with stubs); archived specimens are hidden (BES-07).

- **Paged list (FR-BES-23, NFR-12):** `GET /specimens/cards?timeZone=…[&limit=n][&after=cursor][&location=id|none][&species=id]` answers `{ cards, total, next }`. A page holds `limit` cards (default 100, starting value, assumption; 1 to 200, else `input.invalid` naming `limit`). `after` is the opaque cursor of the last card of the previous page (the URI-encoded JSON of its name and ID); a malformed one is `input.invalid` naming `after`. `location` takes a location ID or `none` for plants without a location, `species` a species ID; a malformed value is `input.invalid` naming its field, a foreign or unknown ID simply matches nothing. `total` counts the whole filter on every page, `next` is `null` on the last page. Order: `lower(name)`, then `id`; the keyset page is one statement in `specimenPage` (`db/src/collection/specimen-locations.ts`), the cards are built by `specimenCardPage` (`core/src/collection/cards/cards-page.ts`) with the same mapping as the AI read (`cardsOf`). A plant added or archived between two pages neither skips nor repeats another one. The key `cards` stays for the current web client, which sees only the first page until stage 2 pages the list.
- **Summary (US-BES-06):** `GET /specimens/cards/summary` answers `{ total, groups: [{ locationId, location, count }], unplaced, anyMeasured, lastLocation }` over all active specimens; `unplaced` is the number of active specimens without a location (the group "Standort unbekannt"). The database answers the counts as aggregates without any name (`specimenCounts`, `db/src/collection/specimen-locations.ts`); `core` resolves the place names through the places of the account (`specimenSummary`, sorted by name). `lastLocation` is the place of the plant with the latest catch date that has one (the rule of the add-plant place field). `anyMeasured` is the port `MeasuredSource` (`care`, `measuredSpecimenIds`: one aggregate of the IDs with a measurement, `db/src/care/measurements.ts`) checked against the active plants by `SpecimenPageSource.anyActive` (`specimenAnyActive`); without a measurement port no plant counts as measured.
- **Treatment list (US-BEH-01):** `GET /specimens/treatable` answers `{ specimens: [{ id, name, location }] }` for every active specimen, cuttings included (`treatableSpecimens` reads the IDs, `specimenTreatable` in `core` adds the place names); `location` is `null` when unknown.
- **One card (US-LIC-02):** `GET /specimens/:id/card?timeZone=…` answers the card the list shows (`specimenCardOf`, bare object). Archived, foreign and unknown IDs answer 404 `specimen.not_found` alike (P-04). The route sits in `api/src/collection/cards/cards-routes.ts` with the three reads above, mounted before `/specimens/:id`.
- **Limits:** the page and the total are two statements in one transaction (READ COMMITTED): a plant added or archived between them can make the total differ from the page by that one change; the next request corrects it.

## Archiving specimens (US-BES-07)

- **Data:** migration 0011 (`-- module: collection`): nullable columns `archived_at` (`date`, read back as text, NFR-08), `archived_reason` (1 to 250 characters, a start value) and `status_before_archiv` on `specimen`, plus the check `exemplar_archiv_zusammen` (status `archived` if and only if date and reason are set). `status` already knew `archived` since 0007. No new table, so no new tenant fixture; the row rule of `specimen` covers the new columns.
- **Operations:** `specimen.archive` (input `specimenId`, `timeZone`, `reason`; the date is the local calendar date of the time zone) and `specimen.restore` (input `specimenId`; restores the status from before, so a Steckling stays a Steckling). Both run in one statement. Archiving twice keeps date and reason of the first archiving (`specimen.already_archived` 409), restoring a non-archived one is `specimen.not_archived` 409, a foreign or unknown specimen is 404 `specimen.not_found`. Measuring an archived specimen is refused with `specimen.archived` 409.
- **API:** `POST /specimens/:id/archive` (`Idempotency-Key`; body `timeZone`, `reason`), `POST /specimens/:id/restore` (`Idempotency-Key`), `GET /specimens/archived` (`{ archived: [{ id, name, speciesName, caughtAt, archivedAt, archivedReason }] }`, newest first). `GET /specimens` and `GET /specimens/cards` leave archived specimens out (the ports of BES-06 never hear their ids); `GET /specimens/:id` still returns them with date and reason.
- **For later evaluations:** every derivation over specimens filters with `isActive` from `core` (distribution, treatments, Pokédex ownership, today list). Care phases already list only `plant` (FR-PHA-04).
- **Web:** button "Archivieren" on each card opens a form (reason from a list or free text), the section "Archiv" below the list shows reason and date with "Wiederherstellen". Success and errors stay visible (P-09, P-10).
- **Limits:** the name of an archived specimen stays taken (assumption: restoring can then never collide), so a new specimen of the same Art needs a marker. Archiving on a swap (US-SOZ-11) comes with SOZ. The measurement history of an archived specimen is readable over the API but has no screen.

Every column is a deviation; `null` means "the catalog applies", so an empty profile is valid. Locations and the zone hang on the own account through composite foreign keys `(account_id, id)`; the species through the plain key `care_profile_species` to `species(id)` (`on delete restrict`), the second user of the registered global reference table (AB-10). ## Measurements (US-WAC-01)

- **Module:** `care` (owner decision O-1: PHA, BEH and WAC live in one module; `core/src/care`, `db/src/care`, `api/src/care`, `web/src/care`). It depends on `kernel`, `catalog` and `collection` (all listed in `modules.config.mjs`).

- **Operation:** `measurement.record` (`core/src/care`). Input: `specimenId`, `timeZone`, `wert` (finite number from 0 to 10000 in steps of 0.5; the bounds are assumptions), optional `date` (a real calendar day, default `localToday(uhr, timeZone)`, not after today in the user's zone: an assumption), optional `qualitaet` (default `gesund`), optional `notiz` (1 to 1000 characters). Invalid input writes nothing; a foreign or unknown specimen is `specimen.not_found`; replays with the same `Idempotency-Key` write once (US-QS-03). The view `messView` is derived (P-01): growth measure of the species ("unbekannt" if the species is not visible), all measurements (newest first), the last one and its quality.
- **API:** `GET /specimens/:id/measurements` (foreign or unknown specimen: 404), `POST /specimens/:id/measurements` (`Idempotency-Key`; body `wert`, `timeZone`, optional `date`, `qualitaet`, `notiz`; 201).

The operation `measurement.photo` (core, `care/measurements/photo.ts`) finds the measurement of the day (`MeasurementStore.findOnDate`, the one recorded last), refuses without one (`measurement.not_found`, 404) and refuses a second photo without `replace=true` (`measurement.photo_exists`, 409), then runs `storeImage` (TE-05) under a new name `<uuid>.webp`, links it (`MeasurementStore.setPhoto`, column `measurement.photo`, migration `0031`, nullable; the name check accepts `.webp` only since `0103`, issue 1289) and deletes the old object afterwards (a failed delete leaves an orphan, never a wrong photo). The route needs `media` (object store and processor) in `createApp`; `main.ts` builds it from the `S3_*` variables, without them the route answers 502 `media.storage_unavailable`. Mapping: `media.too_large` 413, `media.type_unsupported` 415, `media.not_an_image` 422. Reading the photo back (US-WAC-05): `GET /specimens/:id/measurements/:measurementId/photo` answers the stored WebP (`Cache-Control: private`, `Content-Type` image/webp) only for the owner (`measurementPhotoFile`). `?size=thumb` answers the 256 px thumbnail (NFR-12, `ImageReader.read`); without `size` the stored copy. Every address of a photo carries `?v=<version>` (the object name without `.webp`, built by `measurementPhotoPath` in core for the cards, the measurement list, the year in review and the anniversaries): a replaced photo has a new object name and so a new address (NFR-12). The read ignores `v`, `size=thumb&v=…` works too. The year in review answers `photos.first` and `photos.last` with `measurementId`, `date` and `photo` (the object name, the version of its address) and `photos.urls` with the addresses. Any other `size` value, and a repeated `size`, is `input.invalid` (400, field `size`), read nothing. A photo stored before the thumbnail existed answers the stored copy for `size=thumb`, never 404. A foreign specimen is 404 `specimen.not_found`, a measurement without a photo 404 `measurement.photo_not_found`, no storage 502. The web form has the optional upload control and the course shows the photo (fetched with the token, never a public link).
- **Store:** `MeasurementStore.listMany(userId, specimenIds)` answers the measurements of many own specimens in one statement, per specimen in the order of `list` (NFR-12). The achievements (facts, care rhythm, year in review) read through it: one read per kind for all specimens, never per specimen.
- **Limits:** no rate and trend (US-WAC-03, US-WAC-04), no editing or deleting of a measurement, no reminder for old measurements (FR-WAC-08). `Specimen.measurements` in the `collection` view stays an empty list; the measurements are read through their own route.

## Collector cards (US-POK-01, FR-POK-13)

- **What:** `GET /pokedex/cards?timeZone=<IANA>` answers `{ cards }`: one card per species of the taxonomy tree (`core/src/pokedex/cards/collector-cards.ts`, `readCollectorCards`), numbered in tree order. `state` (caught or missing) is derived live from the own specimens (`pokedexOwnership`) and never stored (P-01).
- **Parts of the answer:** the tree (`taxon`, resolved rows; the same for every account, no user data, readable by the application role), the catalog facts of the approved species (`SpeciesPostgres.approvedFacts`, ordered by Latin name and id: when two approved species share a Latin name, the card takes the facts of the first by id; German name, difficulty, light zone), the app rarity (`readAppRarityBasis`, US-POK-14: the counts of consenting accounts) and the caught state. Input that differs per account: the caught state, the catch dates, the photos and the app rarity (consent, specimens of the other accounts). Input the same for every account: the tree, and the approved facts (approved species are visible to everybody, `visible` row rule of migration 0102; no column depends on the account).
- **Cache (FR-POK-13, NFR-12):** only the tree is kept. `sharedTreeCache` (`api/src/pokedex/cards-cache.ts`) is built inside `pokedexRoutes(pool)`, so each app instance has its own entry; no module-level state. One entry: the tree of the newest build, keyed by `TaxonomyPostgres.version()` (`catalog_fingerprint || '@' || built_at`, one row with `limit 1`; `replace` is the only writer and stamps every row alike). Each request reads the version first; on a match the kept tree answers, otherwise the tree is read and kept. A failed version read or tree read is an error for that request and is never kept (P-10). Two concurrent first requests may both read the tree; both answers are right.
- **What moves the version:** a taxonomy build that replaces the tree (job `pokedex.build_taxonomy`, `runTaxonomyBuild`). The fingerprint is a hash of the sorted, normalized Latin names of the approved species with an epithet and no cultivar (`approvedLatinNames`). Approving such a species changes the names, but the stored fingerprint moves only when the queued build has replaced the tree; approving a genus-only species or a cultivar moves nothing, and such a species is not in the tree. A failed build keeps the old fingerprint.
- **What does not move it:** an accepted, reverted or withdrawn correction of `german_name` (`accept_catalog_correction`, `revert_catalog_field`, migrations 0080 and 0086), and the catalog fill (`CatalogFillPostgres.record`, which fills an empty `german_name`) change the facts of an approved species without changing its Latin names. The fingerprint stays, so the facts are **not** kept in the cache: they are read on every request (test: "FR-POK-13 the catalog facts are read per request"). Open decision (owner): version the facts (a counter that those writes move) if the read of the facts becomes a cost.
- **Not kept, ever:** the caught state, photos, catch dates, own proposals, the app rarity and the facts (see above).
- **Storage of the version:** no new table or column; `TaxonomyPostgres.version()` is one read of the existing `taxon` rows.
- **Tests:** `api/src/pokedex/cards-cache.test.ts` (fake source: kept while the version is unchanged, a new build reads again, only the newest entry is kept, failed reads are not kept, concurrent first reads), `api/src/pokedex/pokedex-cards.test.ts` (real database: the answer is byte-identical to the uncached composition, two keepers with different plants in both request orders, facts and rarity per request, a build at the next request, a warm request sends fewer statements), `db/src/pokedex/taxonomy.test.ts` (the version names its build and changes with it).
- **Limits:** the tree is read as a whole, not paged: search, filters and sorting span the whole tree (FR-POK-13). The kept tree costs memory per app instance in proportion to the resolved rows of `taxon`.

- **Hints for wishes without a fitting zone (FR-WUN-03):** `GET /wishes/candidates` also returns `unfit`: every open wish with no target zone (`zone_unknown`) or the cutting light zone (`zone_outside`) as `{ id, title, kind, zone, reason, nextAction }` (`zone` is the name or `null`; derived live, never stored). The name of the cutting light comes from the optional `ZoneStockSource.uncounted`, wired in `zone-stock.ts` from the lowest zone of the account. Nothing is changed or removed (P-10).
- **Stored image (US-WUN-04):** `POST /wishes/:id/image` (with `Idempotency-Key`, no body) runs `wish.store_image` (core `wishlist/image`): only a Wikimedia Commons address is accepted (`commonsTitle`), the metadata come from the Commons API through the source client (new source `commons`, TE-09), the license must be public domain, CC0, CC BY or CC BY-SA (`readCommons`; nothing assumed, a missing license is refused), the original is downloaded from `upload.wikimedia.org` only (`createWikimediaDownload` in `api/src/wishlist/wish-image.ts`: https, no credentials, no redirect, time and size limit), processed by `storeImage` (TE-05) and stored as `<uuid>.webp` (column `wish.image_object`, migration 0042; the name check accepts `.webp` only since `0104`, issue 1289); the wish gets the verified `image_source` (author, file page) and `license`. Answers `{ wish, changed }`; `wish.image_source_unsupported` 422, `wish.image_not_found` 404, `wish.image_license_unsupported` 422, `media.*` and `source.*` from the pipeline; an image that is stored already answers `changed: false` and fetches nothing; `media.storage_unavailable` 502 without storage or sources (`createApp` option `wishImage`, built in `main.ts`). `GET /wishes/:id/image` serves the stored WebP (`Cache-Control: private`, `Content-Type` image/webp) to the owner only (`wishImageFile`): a foreign wish is `wish.not_found`, one without a copy `wish.image_not_found`. `?size=thumb` answers the 256 px thumbnail that the wish cards ask for (NFR-12, `ImageReader.read`); a wish image stored before the thumbnail existed answers the stored copy for it, never 404. Without `size` the stored copy. Any other `size` value, and a repeated `size`, is `input.invalid` (400, field `size`), read nothing. `GET /wishes/candidates` carries `image: { url, source, license, stored }` and never the object name (P-05).
- **Limits:** no way back from "bought" or "discarded" (resetting a wish to open is not built), no purchase date or price (the cost view US-EQU-09 does not exist, nothing is invented), no species field on the wish (the specimen link carries it), no hint list for wishes outside zones 2 to 4 yet.

## Discover suggestions (US-ENT-01)

- **What:** `GET /discover/suggestions?timeZone=<IANA>&deck=<n>` (`deck` from 1, default 1; 400 `input.invalid` for a bad zone or deck) returns `{ deck, suggestions, empty }`. `suggestions` (`core/src/discover`) is derived on every request, nothing is stored (P-01, no table, no migration): the species of the taxonomy tree (`collectorCards`) that are not caught (US-POK-06) and have no wish of any status (name key as in FR-WUN-06). Order: species of a family without a caught species first, then tree order, so the same data gives the same deck (FR-ENT-05). A deck holds 10 cards (`DECK_SIZE`, starting value, assumption, DM-ENT-03).
- **Card:** `species`, `germanName`, `summary`, `family`, `lightZone`, `difficulty`, `imageUrl` and `sourceUrl` (link only, P-05; Wikipedia, CC BY-SA, FR-POK-07), `attributes` (DM-ENT-01: all `null` until the catalog carries them) and 1 to 3 `reasons` (today only "not caught yet" and "new family"); `null` always means "unbekannt" (P-08). No percentage and no "match" (FR-ENT-06).
- **Empty:** `empty` is `null` while there are cards, else `{ reason, text, nextAction }` with `reason` `catalog_empty`, `all_decided` or `deck_exhausted`.
- **Web:** tab "Entdecken" (`web/src/discover`): one card at a time, buttons "Nein", "Später", "Ja" and a swipe (80 px, assumption). "Ja" and "Nein" are written at once (US-ENT-04) and the card moves on only after the write succeeded (an error stays visible, P-10); "Später" writes nothing; a swipe to the right is "Ja", to the left "Nein".

- **Decisions (US-ENT-04):** `POST /discover/decisions` `{ species, decision: "yes"|"no"|"later", timeZone }` (with `Idempotency-Key`) runs `discover.decide` and answers `{ decision, saved }`. The server derives the wish from the suggestion (`candidatesFor`): Yes writes an open wish, No a discarded one, both with `source: discover` and `decided_at` (the local day, NFR-08), Later writes nothing; the Latin name is the wish name, the target zone the account's n-th zone, the license stays unknown. A species that has a wish already writes nothing (`saved: false`); a species that is not suggested is refused with 409 `discover.not_suggested`. Data: migration `0048_wishlist_wish_source.sql` (`wish.source` `manual`|`discover`, default `manual`; `wish.decided_at date`); `WishValues` carries the optional `source`, `decidedAt` and `status`. Private to the account like the wishlist (P-04, FR-ENT-08).
- **Undo (US-ENT-04):** `POST /discover/decisions/undo` `{ species }` (with `Idempotency-Key`) runs `discover.undo` (`core/src/discover/decide/undo.ts`) and answers `{ undone }`. It takes back the account's last Yes or No only: the wish that decision created is removed when it is still that decision (the wish's status is the one the decision gave, no specimen). The mark of that decision is `wish.last_decision` (`yes`|`no`, at most one wish per account, migration `0105_wishlist_wish_last_decision.sql`; a new Yes or No moves it). Refusals write nothing: 409 `discover.undo_not_last` (an earlier decision), `discover.undo_changed` (the wish was bought, discarded or linked since), `discover.not_a_decision` (a wish that is no Discover wish). A species without such a wish answers `undone: false`, also for a repeat or another account (P-04). Port `DecisionStore` (`core/src/wishlist/types.ts`), adapter `DecisionsPostgres` (`db/src/wishlist/wish-decision.ts`); `insertWish` moves the mark in the same transaction under an advisory lock per account (`db/src/wishlist/wish-row.ts`).
- **Preferences (US-ENT-05):** `tallyOf` and `preferenceFactor` (`core/src/discover/preferences`, pure) derive from the own wishes on every request, nothing is stored: open and bought wishes are "yes", discarded wishes "no", attributed through the catalog card of the same name key. The factor of a candidate is the product of `(yes + 1) / (no + 1)` over its known family, genus, light zone and difficulty (1 without decisions, unknown values neutral); the rank is factor x (1 + shares), ties keep the tree order. `preferenceReason` adds "Du hast N Arten der Gattung/Familie X auf der Wunschliste" where yes outnumbers no. No API shape change.
- **Exploration (US-ENT-06):** `explorationPlan` (`core/src/discover/exploration`, pure) groups the species by the order that has no caught species, else by the family that has none (`CollectorCard.order` is new), orders the groups by size (fewest species first) and gives deck n one species from each of the next `EXPLORATION_PER_DECK` (2, starting value) groups, chosen by a stable hash of account, local day (the `clock` of the dependencies, default system clock), deck number and group (FR-ENT-05). `exploringDeckOf` fills each deck to `DECK_SIZE` with the normal ranked cards (never a species that explores in any deck, so no card shows twice) and spreads the exploration cards between them. `Suggestion.exploration` marks them; the web card shows "Mal etwas anderes". No API shape change beyond that field, nothing is stored.

## Job queue and background jobs (TE-06, US-QS-03)

- **Module:** new platform module `jobs` (`core/src/jobs`, `db/src/jobs`, `api/src/jobs`), registered in `modules.config.mjs` with the edge `kernel` only; MON, POK and KI will depend on it, never the other way. ADR 0003 O-1 had put the queue into `kernel` until it grows rules of its own; the lease, retry and merge rules are that growth (assumption, decided by the PO; revisable).
- **Port `JobQueue`** (`core`): `enqueue`, `claim`, `succeed`, `fail`, `counts`, `purge`; time always comes in as a parameter (no I/O in `core`). `enqueueJob` validates and merges, `runNext` / `drainJobs` run due jobs through handlers (`<module>.<job>` to a function). Contract test `queue.contract.test.ts` (in-memory adapter); the PostgreSQL adapter `JobsPostgres` repeats the cases and adds concurrency. Tests that run a worker share one database, so they build it with `onlyTypes` and neither take nor sweep nor purge the jobs of other test files (issue 1259); the API's worker passes none.
- **Repeatable (US-QS-03):** an open job with the same type and dedupe key is merged (unique index in the database); handlers must be repeatable. A failed run is retried with backoff (30 s doubled, at most 1 h, 5 attempts: starting values, assumption); a job without attempts left, or of a type without handler, ends `dead` with its last error and stays visible (P-10). A worker that vanished loses its job after the lease (5 min, assumption) and another worker takes it over; a late result of the old worker is ignored. A job that did not start before `expiresAt` becomes `expired` and never runs late. Finished jobs are purged after 30 days (assumption).
- **Data:** table `job` (migration `0022_jobs_queue.sql`), installation-level, **without account id** (justified entry in `JOBS_TENANT_EXCEPTIONS`): the application role has no rights on it, only the worker (owner connection) does; the payload holds ids, and a handler reaches user data through `withAccount` (P-04). Claiming uses `for update skip locked`.
- **Runner:** `createJobWorker` (`api/src/jobs`) polls every 5 s (assumption) inside the API process (one deployable); a queue error is reported to stderr and retried at the next tick. Handlers are registered in `api/src/jobs/handlers.ts` (empty until the first job type exists).
- **Open:** job types: the taxonomy build (US-POK-03) and the daily reminder `monitoring.send_reminders` (US-MON-01); not yet: photo processing (US-WAC-05) and AI orders (KI), no retry or release of dead jobs by the operator.

## Object storage and image processing (TE-05, FR-WAC-09, QG-D3)

- **Where:** new platform module `media` (`core/src/media`: ports and rules, no I/O; `api/src/media`: adapters), registered in `modules.config.mjs` with the edge `kernel` only (ADR 0003 had it as a module, O-1 had moved it into `kernel`; like `jobs` it has rules of its own); no migration, no route yet (US-WAC-06 builds the upload on it).
- **Port `ObjectStore`** (`core`): `put`, `get`, `delete`, `exists`, always with the account id. The key is built only by `objectKey`: `<account uuid>/<name>`, the name is `[a-z0-9-]` plus `.webp`, so no input leaves the account's prefix (P-04, QG-D3). A foreign or unknown object is `media.not_found`; `delete` of a missing object succeeds. `InMemoryObjectStore` is the pure fake for tests.
- **Port `ImageProcessor`** and `storeImage`: checks name, upload size and type, processes, stores the processed WebP and its thumbnail. The original goes to the processor only and is never stored (FR-WAC-09). The sharp adapter (`createSharpProcessor`) rotates by the EXIF orientation, shrinks to at most 1600 px on the long side, re-encodes as WebP (quality 82, a starting value: assumption, issue 1289) on a white background and writes no metadata (no EXIF, GPS, XMP, IPTC, ICC). The thumbnail (NFR-12) is cut from that stored copy in the same step.
- **Thumbnails** (NFR-12): `thumbnailName` gives `<name>-thumb.webp`, derived from the stored name, so no row and no migration hold it. `storeImage` writes the copy first, then the thumbnail; when the thumbnail write fails the copy is removed again and the upload is refused with `media.storage_unavailable` (502): nothing is kept, the caller can retry, and the measurement keeps its old photo (P-10). `ImageStorage.read(accountId, name, size)` (`imageReader`, also used by `care` through its own port): `thumb` answers the thumbnail, and a photo that has none (stored before NFR-12) answers the stored copy, so the thumbnail size never gives not found. No backfill: such photos stay full size until they are replaced. `ImageStorage.remove` deletes the copy and the thumbnail (replacing a photo, a refused upload). Account deletion (`deleteAll`, by prefix) takes the thumbnails with the copies. Every read is account-scoped like the copy (P-04).
- **Callers per size** (web, `use-stored-photo`): `thumb` (`size=thumb`): the Sammlung tile (`plant-tile`, 56 px, requested when the tile is near the viewport) and the compact picture of a measurement in the history of a plant (`measurement-photo` compact, a card of the paged list, at most 96 px). The stored copy: the overview picture of a plant (80 px; its link opens the large photo, so it keeps the copy), the measure page (`measurement-photo`), the wish image (wishlist card), the achievements photos and the AI assessment (`measurementPhotoById`, the `get_measurement_photo` tool). The wish image has a thumbnail as well (same pipeline), no caller asks for it yet.
- **Limits** (`MEDIA_LIMITS`): 1600 px is fixed by US-WAC-06. The thumbnail has a long side of 256 px (NFR-12, set by the issue). WebP quality 82 for the stored copy (`MEDIA_LIMITS.webpQuality`) and 72 for the thumbnail (`thumbWebpQuality`) are starting values (assumption, owner decision 2026-11-05, issue 1289). Assumptions (starting values): upload at most 15 MB, stored object at most 5 MB, decoder guard 50 megapixels, upload types JPEG, PNG and WebP (everything stored is WebP); the web blob cache holds 200 pictures and 32 MB (`use-stored-photo`, NFR-12).
- **Format** (issue 1289, owner decision 2026-11-05): every stored picture is WebP, the measurement photo, its thumbnail and the wish image. The switch from JPEG is clean: no reader for the old format, no conversion job, no production data. A later format change needs its own migration decision and a fresh backup.
- **Errors** (German texts in `ERROR_TEXTS`): `media.name_invalid`, `media.not_found`, `media.too_large`, `media.type_unsupported`, `media.not_an_image`, `media.storage_unavailable`. HTTP mapping: 413, 415, 422, 404, 502 (first route: US-WAC-06).
- **S3 adapter** (`createS3ObjectStore`, `@aws-sdk/client-s3`): any S3-compatible host, no provider-specific code (hosting TE-03 stays open). Environment: `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (required), `S3_ENDPOINT` (custom hosts, e.g. MinIO) and `S3_FORCE_PATH_STYLE` (default `true` with an endpoint). `s3ConfigFromEnv` names the missing variables; no secret lives in the repo.
- **Local storage:** `MINIO_ROOT_PASSWORD=<password> docker compose -f app/config/dev/storage.compose.yaml up -d` starts MinIO on `127.0.0.1:19000` (user `pflanzendex`). Run the API tests with the `S3_*` variables set (endpoint `http://127.0.0.1:19000`, bucket `pflanzendex-test`, the bucket is created by the test). Without them the adapter tests are reported as skipped with the reason; everything else runs against the in-memory fake.
- **Test host** (US-WAC-06): the overlay `app/config/deploy/docker-compose.store.yml` (opt-in through `COMPOSE_FILE`) runs the MinIO image of the development storage with no published port, and the one-shot `object-store-bucket` runs `packages/api/src/media/ensure-bucket-cli.ts` in the API image before the API starts. `ensureBucket` (`media/ensure-bucket.ts`) creates `S3_BUCKET` idempotently: 30 tries, 2 s apart, while the store does not answer (starting values, assumption); an authorization error fails at once. Runbook: `docs/guides/operations/staging-deploy-and-backup.md`, "Object store of the test environment".
- **Open:** the only route is the measurement photo upload (US-WAC-06, see Measurements; the object name sits in `measurement.photo`, so there is no table `medium`), the overview picture (80 px) loads the stored copy because its link opens the large photo (a thumbnail there needs a second request on click), photos stored before NFR-12 have no thumbnail (no backfill), no access rules for shared photos (SOZ), no virus scan, no backup of the bucket (`docs/guides/operations/staging-deploy-and-backup.md`), no `make` target for the storage container (proposed in the PR), the `sharp` install inside the Alpine API image is untested.

## AI access: the MCP endpoint (E-04, US-KI-07, ADR 0013)

Code: `api/src/ai/mcp` (`protocol.ts` wire format, `tool-call.ts`, `tools/` catalog, `mcp-routes.ts`); own implementation, no SDK (reason in ADR 0013).

## Conditional answers and private caching (NFR-12, issue 1244)

- **ETag on every answer of the account:** each `200` of a protected `GET` carries `ETag`, `Cache-Control: private, no-cache` and `Vary: Authorization` (`api/src/kernel/account-etag.ts`, `hono/etag`). The ETag is a SHA-256 of the body with the account id mixed in. A repeat with `If-None-Match` of unchanged data gets `304` without a body; the `304` keeps the rule, the vary and the CORS headers. A `304` is never answered for the ETag of another account, even when both bodies are equal (`api/src/account-etag.test.ts`, `api/src/kernel/account-etag.test.ts`).
- **Own rule kept, no ETag:** an answer that sets `Cache-Control` itself keeps it and gets no ETag: photos (`private, max-age=3600`), exports and operator data (`no-store`). Errors and writes get no ETag.
- **Web side:** the reference data (species, locations, light zones, unlocks) is shown from a copy for 5 minutes (assumption, `REFERENCE_STALE_TIME` in `app/packages/web/src/shared/data/client/request/query-client.ts`); every write of the account refreshes the copies it can change. Several parts of one screen that read the same key and mount at different times share a copy for 10 seconds (assumption, `SCREEN_STALE_TIME`, same file; issue 1291): the news of friends (`["social", "banner"]`), so a cold start of "Heute" asks once. A first visit asks a second time on purpose, after marking the feed as seen (US-SOZ-06).

## Unlocks by tap and lock states (US-ONB-05)

- **What:** every function of the app with its derived lock state, the reason it is locked and the way to open it, and the keeper's tap that opens a locked function for good. The states are derived on each request and never stored; the tap is the only stored decision (`account_unlock`, DM-ONB-02).
- **Core:** `unlockStates` and `unlockState` (`core/src/account/onboarding/unlock/unlock-state.ts`) derive a state from the counts, dates, keeper style, calm mode and switches; `UNLOCK_FUNCTIONS` and `UNLOCK_RULES` (`unlock-registry.ts`) hold the functions and the starting values. States: `open`, `locked` (with `reasons`, one `ways` entry per condition, `mayUnlockNow` true), `switched_off` (operator; never listed) and `keeper_off` (never announced). The type also has `unlockable`, which no code path produces.
- **Operation:** `onboarding.unlock_function` (`onboardingUnlockFunction`, core `account/onboarding/unlock/open/unlock-open.ts`, P-03) stores the tap once; a second tap keeps the first date and nothing is deleted. A lock is no permission, so the operation does not check the lock state. It refuses an unknown or operator-switched-off function with `onboarding.unknown_function` (404) and a keeper-off function with `onboarding.keeper_off` (409).
- **API:**
  - `GET /onboarding/unlocks?timeZone=` answers `{ functions }`: every function that may be announced, in navigation order, each with `state`, `announced`, `reasons`, `ways`, `mayUnlockNow`, `id`, `epic`, `destination` and `keeperSwitch` (absent for core functions). Operator-switched-off functions are missing; keeper-off functions are listed with `announced: false`, and so are the three achievement functions in calm mode.
  - `GET /onboarding/unlocks/:id?timeZone=` answers one function with the same entry: `200` while open; `409 onboarding.locked` and `409 onboarding.keeper_off` with the entry as data; `404 onboarding.unknown_function` for an unknown or operator-switched-off id.
  - `POST /onboarding/unlocks/:id` ("Jetzt freischalten") with `Idempotency-Key` and body `{ timeZone }` runs `onboarding.unlock_function` and answers the stored row `{ id, unlockedOn }`. A missing key gives `400 idempotency.key_missing`, a bad time zone `400 input.invalid`.
- **Scope:** only the own account (P-04). The AI client reads the same list as `list_unlocks` (`GET /mcp/unlocks`, `unlockListFor`) and never changes it. No route refuses a request because of a lock (FR-ONB-04); the style change of US-ONB-03 reads the states only to record the unlock dates of the functions locked when the keeper moves to `many`.
- **Tests:** `api/src/account/unlock/unlock.test.ts`, `core/src/account/onboarding/unlock/unlock-state.test.ts`.
