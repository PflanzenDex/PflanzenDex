# 18 – Architecture and Quality Gates

As of: 2026-10-02 · **Draft.** Extends the technology draft from `16-Releases-and-Decisions.md` with binding **quality barriers** (quality gates). The model is the rule set of the project AdventskalenderTombola (`~/root/Code-Root/AdventskalenderTombola/`): git hooks, CI pipeline, structure checker, architecture boundaries, coverage thresholds, principles register and definition-of-done lists.

Principle: **A rule that stands only in a document is a wish. A rule that a script checks and that blocks the merge is a gate.** Gates arise step by step (US-QG-06), not all before the first code. **How** gates are triggered and operated (task runner, hooks, routines, skills, process, release) is in `19-Development-Process-and-Automation.md`.

## User stories

### US-QG-01 · Find errors early and locally · 🟨

As a **developer** I want the fast checks to run before the push, so that CI is rarely the surprise.

Acceptance criteria:

- `commit-msg`: a violation of QG-C1 rejects the commit and names the rule.
- `pre-push`: QG-C2 to QG-C5 run together, at most four at a time. A failing check does not stop the others; the run then names every failed check and the command to re-run it.
- The checks run within the time budget of **60 seconds** (assumption) on a normal development machine; what takes longer belongs in CI.
- The same commands exist as `make`/`npm` targets (`lint`, `test`, `ci`), so that locally and CI run the same thing (FR-QG-01).
- **Local caches (issue 1608):** Given a local run of `npm run lint`, `npm run format:check`, `npm run typecheck` or `make gates`, when it runs, then the caches of ESLint, Prettier and `tsc` (`--incremental`) are written under `app/.cache/gates/` only, and that folder is ignored by git and by Prettier. Given a cold folder, when a run starts, then it creates the folder itself. Given the ESLint cache file, when its name is computed, then the name carries a key over `app/eslint.config.js`, `app/package-lock.json`, the rule code and config (`app/tools/check/code/`, `app/tools/check/quality/gates/`, `app/config/lint/`), the baselines and quality limits of `app/config/gates/` that the config reads when it loads, and the source of `core` that the constants rule reads, so a change of any of them starts a new cache. Given a finding that ESLint reported and a second run with the cache, when the second run starts, then the finding is reported again (test: `eslint-shared.test.mjs`).
- **CI stays cold (issue 1608):** Given a CI run, when it starts, then no cache of `app/.cache/gates/` is restored: `setup-app` caches `node_modules` only, and no workflow caches `app/.cache/`. The CI run depends on no local cache.
- **Green result (issue 1608):** the record is one JSON file in the git directory of the worktree, keyed by the content: the tree of the working copy (uncommitted and untracked files that are not ignored), the commit of `origin/dev` (empty when missing), the lock stamp in `app/node_modules`, the Node version and `DUPLICATES_BASE`. Given `make gates` on a content whose record says that it passed, when it runs, then the steps are skipped, the output names the time of the pass and that `FRESH=1` runs them, and the exit code is 0. Given a changed tracked file, a new untracked file, a deleted file, a moved `origin/dev`, a changed lock stamp or another `DUPLICATES_BASE`, when it runs, then every step runs. Given `FRESH=1`, then every step runs and a pass is recorded again. Given a failed run, then the record is removed. Given an edit during the run, then nothing is recorded. Given an error while the key is computed or the record cannot be read, then every step runs and the output says why, and the run is never failed by it. Given `CI` is set, then no record is read or written and every step runs (D-02). `make gates` runs `secrets` and `workflows` before the check, every time (test: `run-gates.test.mjs`).

### US-QG-02 · CI decides on the merge · 🟨

As a **developer** I want a release (merge from `dev` to `main`) to happen only with a green pipeline.

Acceptance criteria:

- Jobs: fast checks (secrets), lint/types/structure/boundaries, tests with coverage, security check, integration, end-to-end, Lighthouse, docs (QG-S1 to QG-U3).
- A collective status "ci-status" is the only required check (FR-QG-02); individual jobs can be reorganized without changing the rule. Since 2026-10-03 the repo is public and rulesets protect `main` and `dev` (ADR [0001](../../adr/0001-public-repo-and-rulesets.md)): merge only via pull request with a green "ci-status". A merge into `main` needs one approval from a human who is not the last pusher (ADR [0001](../../adr/0001-public-repo-and-rulesets.md); admins may merge their own PRs). A merge into `dev` needs no approval (ADR [0005](../../adr/0005-agents-merge-into-dev.md)); agents merge into `dev` only through `make merge`. In addition the release workflow checks the status.
- **Scope control** (E-13): PRs to `dev` get the fast gates plus unit and integration tests; the **full suite** (end-to-end, Lighthouse, audits) runs for PRs from `dev` to `main`, nightly on `dev`, on manual start and on dependency updates; feature branches get the fast gates locally and via pre-push. That saves Actions minutes (free plan: 2,000 per month, assumption: sufficient, to be measured) without endangering `main`.
- New pushes cancel running runs of the same ref (concurrency).
- **No CI on drafts:** Given a pull request that is a draft, when it is opened, pushed to or edited, then no job of `ci.yml` and no CodeQL analysis runs. The aggregate job reports as `draft-no-ci` on that head, so no check named `ci-status` exists until the PR is ready (a skipped required check would count as passing). Given the draft is marked ready for review, when that event arrives, then the full run starts on the head (issue 1608).
- **One run per ready PR:** Given a run that starts with `ready_for_review`, when a later push to the branch arrives, then that run is cancelled like any other run of the branch. Only a title or body edit (`edited`) and a draft run have their own concurrency group, so neither cancels the run that tests a commit. Given a draft `synchronize` run that GitHub starts after the `ready_for_review` run of the same head, when it starts, then it does not cancel that run (issue 1608).
- **Superseded edit:** Given an edited run whose PR head is no longer the commit it tests, when it runs, then `reuse` answers `none` for every job and no heavy job runs. Given the head cannot be read, then the jobs run in full (issue 1608).
- **One results job:** Given a run in which the app test jobs or the one-screen or a11y-routes shards run, when the run ends, then the job `results` fails unless every part that ran passed: the coverage ratchet when both test jobs passed, each shard set together with its merge (every screen and size measured exactly once, US-QG-01), and no test job that failed or was cancelled. Given a green `results` on a head, when a later edited run starts on that head, then `reuse` may take it as the proof for the test jobs and the shards (issue 1608).
- **UI gates follow UI changes:** Given a change whose files are all workflow or dev tooling, hooks, documentation or Markdown, when the run starts, then `app-ui`, `ds-snapshots` and `lighthouse` do not run, while `app-gates`, `app-tests` and `app-tests-web` still run. Given a change to any other app path, then the three UI gates run (issue 1608).
- Every job has a time limit; exceeding it is an error, not silent hanging.
- **Local run** (issue 1636): Given a developer who runs `make ci`, when its parts run (secrets, workflows, database, gates, tests, coverage, UI build), then they run one at a time and a failed part does not stop the others. When the run ends, then every failed part is listed with the command that re-runs it, and the exit code is 1 when any part failed. The CI jobs keep their own `make ci-*` targets.
- Error messages name the violated rule and the file (not just "failed").

### US-QG-03 · Architecture boundaries are checked by machine · ✅

As a **developer** I want layer violations to be noticed not by review but by a script.

Acceptance criteria:

- The rules from FR-QG-21 (which replaces the proposal FR-QG-04) and FR-QG-05 are implemented as check scripts and have **their own tests** (like `check_project_structure_test.py` in Tombola).
- A violation aborts QG-C4/QG-C5 with rule ID (e.g. `AB-2`) and path.
- Known, deliberately accepted legacy items are in an explicit exception list in the script, **with a comment why**; new entries are not allowed (only reviewers with a reason). The list may only get shorter.
- Exception per file by marker in the first 5 lines (`STRUCTURE_IGNORE: <reason>`, `MAX_LINES_IGNORE: <reason>`); a marker without a reason is itself an error.

### US-QG-04 · Spec, code and test visibly belong together · 🟨

As a **developer (or AI)** I want to get from each story to its tests and back (P-06).

Acceptance criteria:

- Every story in `docs/specs/product/` with status ✅ has at least one test whose name carries the story ID (e.g. `US-PHA-01`). A skipped or todo test does not count, because it cannot fail.
- A test that names an unknown or ⬜ story ID is reported (hint, no error).
- The script additionally checks the consistency of the spec itself: IDs unique, status overview in `README.md` matches the files, references to `US-/FR-/DM-/E-` IDs point to existing entries (references to IDs of the prototype folder are marked as such and excluded).
- A change to domain logic without a green story test does not count as done (DoD, FR-QG-10).

### US-QG-05 · Privacy and tenant isolation require tests · ✅

As an **operator** I want the most sensitive rules never to be merely intention.

Acceptance criteria:

- QG-D1: a test suite creates two accounts and proves for **every table with an account id** that account A reaches no row of account B, except via friendship and sharing. A new table with an account id without this test stands out (FR-QG-07).
- QG-D2: for every social output there is a **field whitelist**; a contract test fails as soon as a field outside the whitelist appears (location, measurement notes, treatment agents, prices; US-SOZ-04, FR-EQU-08).
- QG-D3: a test image with EXIF GPS is uploaded; the stored image contains no EXIF data and the long side is ≤ 1600 px (US-WAC-06).
- QG-D4: a test proves that date and phase calculation run in the user's time zone (NFR-08); a lint rule forbids `toISOString().slice(0, 10)` for calendar dates (cause of B-01 in the prototype).
- QG-D5: a script replays the migrations into a schema model and fails when a foreign key (including composite `(account_id, x)` keys) or a tenant column `account_id` is not covered by the leading column(s) of an index, primary key or unique constraint; without such an index every delete in the parent table and every query of one account scans the table (P-04). Existing gaps are listed in `app/tools/check/code/db-indexes/findings-baseline.json`: a new gap fails, a covered entry must be deleted, the list never grows. Closing a gap is a migration (US-DEV-07).
- QG-D6: an API integration test seeds two keepers (5 and 50 specimens, each with locations, measurements, treatments, shares, offers, swaps with friends, dormancy dates and equipment) and calls every GET route of the app: each route is measured or listed with a reason in `EXCLUDED`, so a new route fails until it is covered. ### US-QG-06 · Gates mature instead of blocking what nobody can meet · 🟨

As a **team** I want to introduce new rules without stopping work.

Acceptance criteria:

- Every rule lives in the **principles register** (`docs/guides/principles/`) with maturity `observed → measurable → checked → gated` (format as in Tombola: _why better, how measurable, checkable by, gate, evidence_). A script validates the register (required fields, maturity matches fields).
- A new gate starts as a **report** (R) with a measured baseline and becomes **blocking** (B) only after an agreed period. Model: Lighthouse at Tombola was first a report, then a merge gate, after the values were reachable.
- Coverage thresholds are set just **below** the current value and only raised (ratchet), never lowered without a reason in the PR.
- A gate that found no error in three months is checked for usefulness, not kept blindly.

State of implementation: criterion 1 is met. Every gate has an entry in `docs/guides/principles/` (PRIN-012 to PRIN-067; PRIN-001 to PRIN-011 were there before, PRIN-009 is now `gated` for the pull request title). The validator `npm run principles` checks the format and the referenced paths and make targets (PRIN-012). Criterion 3 is met as a mechanism: `app/tools/check/quality/coverage/check-coverage-ratchet.mjs` fails when a coverage value drops below its threshold in `app/config/gates/coverage-thresholds.json` and hints when a value can be raised (PRIN-029). The values were set from CI runs; this text does not re-measure them.

**Decided and built (owner decisions 2026-11-06, issue 1516):**

- **Criterion 2 (report, then blocking after an agreed period).** A `checked` entry may carry `blocking_from: YYYY-MM-DD`. `npm run principles` fails when a `gated` entry still carries it (PRIN-5), and when the date is not a real day or has come while the entry is not `gated` (PRIN-6). Report-only gates today are PRIN-043 (`image-scan`), PRIN-061 (`lighthouse-signed`), PRIN-062 (`perf`) and PRIN-067 (the scorecard). Open: their dates, which need the owner; no entry carries one yet.
- **Criterion 4 (a gate without a caught error for three months is checked).** A line `Caught: YYYY-MM-DD, PR #<n>, <what it caught>` in the Evidence section of a gate is written in the PR that fixes the failure and validated by PRIN-7. `make principles-review` lists every `gated` and `checked` entry without such a line in the last three months; for each, the owner keeps it with a reason in its Evidence or lowers its maturity. The routine is manual, once per quarter (`19-development-process-and-automation.md`). Open: the first review.

### US-QG-07 · AI agents work within the same gates · 🟨

As a **developer** I want Claude (or other agents) to be bound to the same rules.

Acceptance criteria:

- `AGENTS.md` in the repo names architecture, structure rules, error handling, test style and refers to the spec; `CLAUDE.md` includes it.
- Task-specific **playbooks** (e.g. "add a new operation", "implement a new epic") live as skills in the repo; the agent checks before improvising whether one fits.
- Before "done" the agent runs `make ci` (or the equivalent) and reports the result honestly (pass/fail), not just "should work".
- The agent does not commit unasked; it changes no gates or thresholds to get around a failure (exceptions need a reason in the PR).
- The Claude Code hook asks a human before the first edit of each gate file on a branch. The edit that went through is recorded in the git directory of the worktree (not tracked, not shared with other worktrees), keyed by branch; later edits of that file on that branch ask nothing. Another gate file, the same file on another branch or in another worktree, and a detached HEAD ask again. A record that is missing, unreadable or malformed asks (fail closed), and an edit of the record itself asks. Applied migrations and the rule for baselines that grow do not change.
- **One approval per ticket (issue 1608):** Given `make gate-plan FILES="<gate file> ..."` (paths relative to the top of the worktree), when it runs, then the gate files are recorded as the plan of the branch in the git directory of the worktree, and nothing is confirmed. Given a path that is not a gate file, when the command runs, then it is refused, names the path, and writes nothing. Given a planned gate file whose first edit asks, when the question is shown, then it lists every planned file of the branch that is not confirmed yet and says that confirming this edit confirms them too; when the human answers yes and the edit goes through, then every listed file is confirmed on that branch. Given a file outside the plan, then its question names that file alone, as before. Given a plan that changed after a question, when the answer is recorded, then only the files that the question showed are confirmed. Given a denied question, then nothing is confirmed, and an edit that no question of its own asked about confirms nothing. Given a plan or question record that is missing, unreadable or names a path that is not a gate file, then every gate file asks alone (fail closed). An agent can propose a list, never confirm one: the plan and the question record are written by the hook and `make gate-plan` only, and an edit of either asks (test: `worktree.test.mjs`, `gate-confirmations.test.mjs`).

### US-QG-08 · Complexity stays manageable · 🟨

As a **developer** I want code not to become unreadable unnoticed, because complexity is the most expensive quality problem: it makes tests hard, changes risky and AI changes unreliable.

Acceptance criteria:

- QG-K1 to QG-K4 run in CI; QG-K1 additionally in pre-push (fast, ESLint only).
- **QG-K4 implemented** (`make duplicates`, part of `make gates`): Fallow `dupes` with the values from `app/config/gates/quality-limits.json` (section `duplicates`: from 3 copies, at least 50 tokens and 5 lines, mode `mild`; starting values, assumption). A clone group that touches a file changed since the base branch is blocking; the overall stock is only reported. Tests are excluded (Fallow default). Measured baseline: 0 groups from 3 copies, 1 group with 2 copies, 0.64 % duplicated lines.
- **QG-K5 implemented** (`make dup`, part of `make gates`, FR-QG-10, US-QG-07): jscpd with `app/.jscpd.json` (TypeScript, TSX and JavaScript in `app/packages`; at least 50 tokens and 5 lines; starting values, assumption) and the limit `dup.maxPercent` in `app/config/gates/quality-limits.json`. Complements QG-K4: QG-K4 blocks clone groups with 3+ copies in changed files, QG-K5 bounds the share of duplicated lines in the whole project. Target: 1 % (owner decision); starting value 1.65 % measured on 2026-10-06 (assumption). The gate fails above the limit (DUP-1) and when the measured value is more than `slackPercent` below the limit (DUP-2, lower the limit). Operation: `app/tools/check/quality/duplicates/README.md`.
- **Stricter domain logic:** in `core` (phases, trend, milestones, swap states, reminders) the narrower limits apply, because it is pure and easy to decompose. A function that breaks the limit is decomposed, not excluded.
- **Diff principle:** only what the PR **worsens** is blocking (new or changed functions above the limit). Existing excesses are in a baseline list that may only get shorter (ratchet, US-QG-06). That way the gate can be armed from day 1.
- **CRAP instead of pure complexity:** a complex function is allowed if it is well tested; it is not if it is complex **and** untested. This couples the complexity gate and coverage (QG-T1).
- A file length over 200 lines (QG-C2) and a function over the complexity limit are **two separate** findings; merely splitting files because of the line count without reducing the complexity does not count as a fix (observation from Tombola: several files were split only "because of the 200-line limit").
- Exceptions by marker with a reason (`COMPLEXITY_IGNORE: <reason>`), visible in review and counted; the number of markers is a metric in the quarterly report (US-DEV-03).
- The health report (Fallow `health` or equivalent) appears as a job summary with the five worst functions, not as a wall of numbers.

Implementing the rules as a check script and moving the existing code are tasks of their own (FR-QG-19).
