# 14 – Epic QS: Cross-Cutting (Privacy, Security, Mobile, Quality)

Non-functional requirements for all epics. All ⬜. The yardstick is the product principles P-01 to P-12 (`00-Product-Overview.md`).

## User stories

### US-QS-01 · Nothing depends on remembering · 🟨 (prototype 🟡)

As a **plant keeper** I want the system to report need for action itself.

Acceptance criteria:

- Phase changes, due treatments, overdue measurements and wishlist buffer trigger a reminder (epic MON) without the app being opened.
- The home screen "Heute" shows the same items (one source, `FR-MON-03`).

State of implementation (enabler TE-07, assumptions decided by the PO, flagged): the module `today` (read only, no table) holds the one `status` function (`todayStatus` in `core`, `GET /today?timeZone=<IANA name>`, view "Heute"). It does not recompute anything; it reuses the derivations of the open treatments (US-BEH-02), the care phases (US-PHA-02) and the hints about incomplete specimens (US-BES-08), reads the clock once and adds order and next action, so "Today", the reminders (MON) and the AI daily status (US-KI-02) can use it and never disagree (R-04). Dates are local calendar days in the user's time zone (NFR-08). Entries, most urgent first (what is bound to a date comes first; assumption): (1) treatment overdue, the most overdue first, (2) treatment due today, (3) phase deviation (location id differs from the target location of today's phase, US-PHA-02), (4) incomplete specimen (US-BES-08), inside groups 3 and 4 by name. Every entry carries a text, a next action (P-09) and the place where it is done (`treatments`, `care_phases`, `hints`; the interface maps them to views). A specimen without location is named once, as incomplete data, not again as deviation (P-10 without duplicates). Treatments that are not due yet are not entries but are counted (`upcoming`, shown as a note), so nothing disappears silently (P-10). An empty list says "Heute steht nichts an" with the count of later dates and leads to the collection (P-09). Archived specimens never appear (`isActive`, US-BES-07), only the own data is read (P-04). **Open (gap list):** the entry "measurement overdue" (needs an interval per species or specimen, which no story defines yet; P-08, no invented number), the wishlist buffer warning (US-WUN-02, still its own view), "phase change today with the old location" (US-MON-02), the QS-04 deviation view, a switch of the AI daily status (US-KI-02) onto the function, reading of the same function by the reminders (US-MON-01 to MON-03), a per-entry quick action in the list (ticking off a treatment still happens in "Behandlung"), the list on the start page, and a count badge on the navigation entry.

- Every story with status ✅ has at least one test whose name carries the story ID (P-06).

### US-QS-03 · Repeatable without fear · 🟨 (prototype ✅)

Acceptance criteria:

- Every writing operation is idempotent or prevents double execution (double click, repeat after abort).
- Background jobs (reminders, catalog enrichment, photo processing) deliver the same result on repetition.
- Given a write under an idempotency key was completed, when the same key comes back with other content, then the answer is `idempotency.key_conflict` (409) and its body carries the saved result in `error.data.saved`, in the shape the first answer had. Given the same key comes from another account, when it is sent, then that account's write runs as a new write and never receives the saved result of the other account (P-04, P-05).
- Given a write under an idempotency key is still running, when the same key comes back, with the same or with other content, then the answer is `idempotency.in_progress`, as before: the app says to wait and asks again, and no conflict banner shows.
- Given a secret operation (`op.secret`, a result shown once such as an invitation code), when it succeeded and its key comes back, then it never returns a stored result: its key was released after the success, so the call runs again (US-ACC-05).
- Given the answer is `idempotency.key_conflict` with a saved result, when the keeper sees it, then the banner names what is saved: "Gesichert ist: {saved}. Deine Änderung ist noch nicht gesichert." for a write that describes its saved result (a measurement, a new plant), otherwise "Deine erste Eingabe ist gesichert. Deine Änderung ist noch nicht gesichert." Its only control is "Hinweis schließen"; dismissing it frees the key, so the next tap is a fresh write. Every write of the write layer (`useWriteAction`) offers this control in the notice that shows the refusal, a toast included (the key is freed when the toast is gone); a write that uses the repeat guard directly (`useRepeatKey`, `runRepeat`) offers it too when its conflict holds the key, that is a create or an append (`withConflictDismiss`): the plan of treatments, a new leaf, a species proposal, the operator's invitation codes, the CSV import, the first plant and a new light zone or location do, so every create and append has the control. A set-state write (a site with `entityKey` or `accountKey`) is left without it on purpose: its conflict frees the key at once (`settle()`), so the keeper is never blocked and a dismiss would only remove a stale notice. **Open:** the control "Änderung sichern" (replace the saved entry through an edit operation with a fresh key, P-03) is not built; it follows with #2460 (measurement correction, `measurement.correct`) and #2461 (specimen edit).

State of implementation: the job queue (TE-06, PostgreSQL, module `jobs`) exists: orders with the same type and key are merged, a failed run is retried with backoff, a lost worker loses its job after a lease, and a job that cannot succeed ends dead with its error kept (P-10). Handlers must be repeatable. A write whose answer was lost keeps its repeat-guard key until it is answered: a retry by the user and the redelivery of a buffered write send the key of their action, so the API writes once. The key is made once, when the user acts, and `useWriteAction` holds it per action: the action names its target and its operation, and never the body. Creates and appends name the operation only (a daily append adds the local day, which names the occasion); a set-state update names the operation and at most a discrete chosen value (a rights value, yes or no, a status), and free text or a whole form stays out. Targets: a create has its own target `new:<entity>` (`createKey`); an append or a set-state names the entity and its id (`appendKey`, `entityKey`); `accountKey` holds only account-level set-state (the profile, the style, the reminders, the deletion). A background write (a seen mark, a feed mark, the zone defaults) takes a fresh key per send and holds nothing, so it frees nothing. At the answer, by class: an `idempotency.key_conflict` of a create or an append keeps the held key, because the server refused that key with another body and an earlier write under it has landed or still runs, so the keeper gets no second record; that key is freed by the dismissal of the conflict banner (US-QS-03 criteria above), by its own answer (a success or another refusal), by `forgetRepeatKeys` (sign-out) or by a reload. A conflict while the first write still runs is `idempotency.in_progress` (the key is kept, as for every lost answer); the server tells a conflict after the first write is done (`done`, with the saved result) from one while it runs (`core` `Begin`, `IdempotencyPostgres.begin`). An `idempotency.key_conflict` of a set-state frees the key, since it only sets state: the next tap is a fresh write. A success frees the held set-state keys of its target, so an archive, a restore and a second archive are three writes; a success never frees a held create or append of its target; any other refusal frees the key of its own action only. A lost answer, `idempotency.in_progress` and an answer that never reached an operation (no token: `access.not_signed_in`) keep the key. Offline, a write is buffered before the token is asked, and the buffer reads the token again on delivery. A bulk write derives the key of each entry from the key of its action. `createWrite` sends the key it is given and compares no content: a key that comes back with another body gets `idempotency.key_conflict`, and the original body under that key gets the stored answer. The buffer keeps each offline write as plain data (method, URL, body, key) until it is answered, in memory until the page closes. Every write route needs the `Idempotency-Key`: the engine checks it first, and `write-key-routes.test.ts` walks every non-GET route of the app without one, each answering `idempotency.key_missing`, apart from the named exceptions in that test. **Open:** keys and buffered writes that survive a reload of the page (US-QS-07).

### US-QS-04 · Deviations become visible · 🟨 (prototype ✅)

Acceptance criteria:

- Wrong location, overdue treatment, buffer undercut, etiolated last measurement, data gaps appear as a warning with an instruction for action (P-09).
- Data that would be missing in an evaluation (specimen without species, without location) appears in a warning list (P-10).

State of implementation: the today list (TE-07, view "Heute") shows every deviation as an entry with a state word, a text and the next action (P-09): wrong location of the care phase (US-PHA-02), overdue treatment (US-BEH-02), etiolated last measurement ("Vergeilt", leads to measuring), zone 2 to 4 below the buffer of open candidates ("Nachschub", the warning of US-WUN-02, leads to the wishlist) and data gaps (US-BES-08, specimen without location or zone, also in the warning list "Fehlt noch"). A specimen always has a species (required on creation), so "without species" cannot occur. Archived specimens are left out (US-BES-07). **Open:** the manual test protocol in a real browser.

### US-QS-05 · Privacy and control · 🟨 (prototype ✅ partly)

As a **plant keeper** I want to know and determine what happens with my data.

Acceptance criteria:

- Information, export and complete deletion of the account (see `US-ACC-04`).
- Photos are freed of EXIF/GPS before storage and reduced to a maximum size (long side 1600 px, WebP quality 82, thumbnail 72; starting values, assumption, issue 1289).
- Location, growth notes, treatments, prices and financial data are never transmitted to friends or partners (FR-SOZ-01, FR-EQU-08).
- A page "What is measured?" names usage measurement and click counting; without consent nothing is counted.

State of implementation: photos are freed of EXIF/GPS and reduced (long side 1600 px, WebP quality 82, issue 1289) before storage and served only to their owner (US-WAC-06). Friends see only the whitelisted facts of shared specimens (US-SOZ-04); a test proves for every friend view (shared specimens, friend collection, friend list, feed, feed banner) that location, measurement notes and treatments of a shared specimen never reach the friend. The section "Nutzungsdaten" on the page Konto ("Was wird gemessen?" until issue 1813) names what is recorded: no click counting, no usage analytics and no advertising or analytics services; the time of the last activity is stored on every sign-in and the operator sees only the number of active accounts of the last 30 days (US-ACC-05); images of collector cards and suggestions are loaded by the device directly from Wikimedia. Export and deletion of the account exist (US-ACC-04); **open:** the information about the processing (release R3); whether the count of active accounts needs a consent or rests on the operator's legitimate interest (owner decision).

### US-QS-07 · Usable on mobile · 🟨 new

As a **plant keeper** I want to operate the app on the phone next to the plant.

The look and the components that make this possible are governed by the design system (`docs/guides/reference/design-system.md`, enabler TE-17, gates QG-U4 to QG-U6).

Acceptance criteria:

- Given a phone of 360 x 640 px (starting value, assumption), when I run each everyday flow (measuring with a photo, watering, ticking off a treatment, opening Heute), then every view fits the width without horizontal scrolling, and the main action of the flow lies in the lower half of the window (starting value, assumption). Exceptions: the layer "Behandlungen" opens from the top of the window, so its rows are outside the lower-half rule (US-QS-18), and the confirming action of a form ("Messung sichern") sits in the bar of the form at the top (SG-SHEET-04, US-QS-32).
- The app is installable (home screen).
- Taking a photo offers the camera: on a touch device each photo field has two buttons, "Foto aufnehmen" (opens the camera) and "Foto wählen" (an existing photo); both accept only image types and feed the same upload. With a fine pointer only "Foto wählen" shows. Reason (issue 1820, found on an Android phone on 2026-11-10): the photo picker of Android shows the gallery and no camera, so one field without `capture` no longer offers both.
- Given a page or a request is loading, when the wait is shown, then an animated sprout (static under reduced motion) accompanies the placeholder or stands alone, and assistive technology hears the loading text once (4.1.3, 2.3.3).
- Given a dialog or a sheet whose code is not loaded yet, when I open it, then the status "Fenster wird geladen …" appears only after 300 ms (starting value, assumption, issue 1575): a window whose code is there, or arrives within that time, opens with no status and no flash, and the status goes when the window opens (NFR-12, P-10).
- Given the status shows, when I press Escape, then nothing opens afterwards (NFR-12, P-10).
- Given the status shows, when I leave the page, then the status goes and nothing opens on the new page (NFR-12, P-10).
- Given a write succeeded or failed, when the result is shown, then a toast says so in a polite (error: assertive) live region above the bottom bar, an undo action is offered where one exists, and the toast stays while it is hovered or focused and for an error at least 10 s; a state that lasts (offline, unknown zone, failed sync) is shown as an overlay bar that stays until dismissed or resolved (4.1.3, 2.2.1, P-10; the overlay rule is the next criterion). The toast also shows above an open layer, so the undo can be seen and taken there (issue 1028).
- Given a form in a layer, when its write succeeds, then the layer closes, a toast names what was saved and the focus returns to the opener; given a refusal, the layer stays open with the error at the field (owner decision D10, issue 1696).
- Given a write confirms or refuses, when the result is shown, then it is a toast and nothing is inserted above the content that is visible, so the list, the form or the layer does not move (DS-54); a refused code stays at its field (P-10).
- Given a card, a person or plant picture, or a progress value is shown, when it is read by assistive technology or the image fails, then a card that opens something is one link or button with a visible focus ring and a 44 px target, a picture is named (or hidden when the name is next to it) and falls back to initials, and progress is a named progress bar with its value or "Schritt n von m"; motion stops under reduced motion (1.1.1, 2.4.7, 2.5.8, 4.1.2).
- Given a set of tabs, when I move with the arrow keys, Home or End, then focus and selection move together over a real tablist (only the selected tab is in the tab order, `aria-selected` and `aria-controls` are set) (4.1.2, 2.1.1).
- Given a collapsible section such as a care profile part, when I toggle it with Enter or Space, then its button reports `aria-expanded`, the height animates with the motion tokens, and under reduced motion it switches without animation (4.1.2, 2.3.3).
- Given a popover or an overflow menu is open, when I press Escape, press outside or tab out, then it closes, and Escape returns focus to its trigger; in the menu the arrow keys, Home and End move over the enabled items (2.1.1, 2.4.3).
- Given a long list such as the species catalog, when its end comes into view and the next part loads by itself (US-QS-15, owner decision 2026-11-21, issue 2412; no "Mehr laden" button and no numbered pages), then the loader row shows without shifting the layout, the screen reader reads "Weitere werden geladen …", the focus stays where it was, the end marker ("Das waren alle 84") and a retry row ("Der Rest konnte nicht geladen werden." with the button "Erneut versuchen") can be reached by keyboard and screen reader, and the button of the retry row is a target of 44 px (4.1.3, 2.4.3, 2.5.8, 4.1.2; owner answers 2026-11-21, issue 2415).
- Given a key-conflict banner of a repeated write is shown (US-QS-03), when the phone is 360 px wide or the text is 200 %, then the banner wraps its text inside the window, never truncates it, and keeps "Hinweis schließen" in reach (P-10, DS-54).

State of implementation (issues 1644 and 144): every write result is a toast (`useSay`): "Gesichert", archived and restored, the Kennzeichen, "Gegossen", the catch date, the light zone, the creation, the invitation code and a refused photo (its refusal stays a toast; a field check stays at its field). A confirmation is a `role="status"` toast in the polite region; `toast.test.tsx` and `announcer.test.tsx` carry US-QS-07. The growth note of "Messen" is a dismissible overlay below the focused field of the form (US-QS-15, DS-54). Proof of the criteria that remain: the sideways scroll of every view at 360 x 640 px and 390 x 844 px is measured by the one-screen gate (QG-U8); the four everyday flows at 360 x 640 px are walked by the mobile e2e test `tests/accessibility/mobile/everyday-flows.spec.ts` (US-QS-07), which checks the width of the page and of its main area and the lower-half position of the main actions, except the rows of the layer "Behandlungen" (it opens at the top of the window). The e2e stack has no image store, so the walk accepts a measurement saved without its photo; the photo upload itself is checked on the owner's phone. Installability: US-QS-26 (install sheet and icon shortcuts), US-QS-27 (a new version on the next start) and US-QS-28 (the install offer in Konto). Camera: the unit test "US-QS-07 taking a photo offers the camera" in `measure-page.test.tsx`. Loading, layers and leaving: the status after 300 ms, Escape and leaving the page are tested in `loading-state.test.tsx` (DS-40) and `overview-page-change.test.tsx`; the sprout and the loading text in `request-state.test.tsx` and `load-more.test.tsx`. Controls and content: tests named US-QS-07 in `card.test.tsx`, `avatar.test.tsx`, `progress.test.tsx`, `step-indicator.test.tsx`, `tabs.test.tsx`, `accordion.test.tsx`, `popover.test.tsx`, `menu.test.tsx`, `load-more.test.tsx`, `pagination.test.tsx` and `responsive-modal.test.tsx`. Open, checked on the owner's phone after the release (R1): the one-handed feel and a real-phone install; plus a screen reader pass. Status stays 🟨 until then.

### Accessibility (US-QS-08 to US-QS-13)

The conformance target is **WCAG 2.1 level AA** as required by **EN 301 549 V3.2.1** (chapters 9 web and 11 software; decision E-23). The stories below turn that target into checkable behavior at app level. Component-level rules (focus ring, 44 px targets, contrast, overlays) stay in `docs/guides/reference/design-system.md` (DS-15 to DS-20, DS-37, DS-38, DS-40) and the gates QG-U1 and QG-U5. The bracketed numbers name the WCAG 2.2 success criteria a criterion covers. The criteria of US-QS-08 to US-QS-12 are **standing criteria**: once done, they hold for every view, flow and control added later. The Definition of Done (FR-QG-10, item 11) and the gate QG-U7 (FR-QG-24) enforce them on every story, so accessibility is not a one-time effort.

### US-QS-08 · Operable by keyboard alone · 🟨 new

As a **plant keeper who cannot or does not want to use a pointer** I want to reach every function with the keyboard.

Acceptance criteria:

- Given any view, when I use only Tab, Shift+Tab, Enter, Space, Esc and the arrow keys, then I can reach and trigger every function the view offers, in an order that follows the visual reading order (2.1.1, 2.4.3).
- Given any view, when I press Tab first, then a "Zum Inhalt springen" link appears and moves the focus past the navigation to the main content (2.4.1).
- Given a focused element, when sticky parts (bottom navigation, header, open sheet) are shown, then the focused element is never completely hidden by them (2.4.11).
- Given a function that uses swiping or dragging (swipe suggestions in Discover, dragging a sheet, reordering), when I use the keyboard or a single tap, then the same result is reachable without the gesture (2.5.1, 2.5.7).
- Given any widget, when it has the focus, then the focus can always leave it again with the keys named above; there is no keyboard trap (2.1.2).
- Given an everyday flow (US-QS-07: measuring with photo, confirming watering or location, ticking off a treatment, Today list), when its end-to-end test runs, then a keyboard-only variant of the test passes (guardrail, P-06).
- Given the shortcut overview opened from its help button, when I press Esc, then the focus is back on that button; opened with `?`, the focus goes to the heading of the view and never stays on `body` (2.4.3, DS-40).

### US-QS-09 · Oriented and guided through the app · 🟨 new

As a **plant keeper using a screen reader, magnification or with limited concentration** I want to always know where I am and what comes next.

Acceptance criteria:

- Given any view, then it has a unique German page title ("Heute – PflanzenDex"), exactly one main heading and the regions header, navigation and main content (2.4.2, 1.3.1, 2.4.6).
- Given I change the view, when the new view has loaded, then the focus moves to its main heading and the new title is announced; going back restores the focus to the element that opened the view (2.4.3).
- Given a flow with more than one step (onboarding, creating a specimen, measuring with photo), then every step shows "Schritt n von m" and its name, going back keeps what I already entered, and I am never asked twice for data I gave in the same flow (3.3.7). The first-use flow and the staged functions follow epic ONB (US-ONB-01, US-ONB-05, US-ONB-06): locked entries stay visible with reason and way, the overview "Was die App kann" is in the help entry.
- Given a help or contact entry, then it is in the same place in every view (3.2.6), and navigation entries keep their order and names across views (3.2.3, 3.2.4).
- Given sign-in or sign-up, then no step requires solving a puzzle or remembering a code by heart; pasting passwords and codes and password managers work (3.3.8).
- Given a view has nothing to do, then it says so and names the next step (P-09), also for screen reader users.

### US-QS-10 · Changes are announced, not only shown · 🟨 new

As a **plant keeper using a screen reader** I want to hear what the app did, without losing my place.

Acceptance criteria:

- Given I save, delete or tick off something, when the operation finishes, then the result ("Gesichert", "Behandlung abgehakt") is announced without moving the focus (4.1.3).
- Given I am offline, when a write action is buffered or delivered later (US-QS-03, US-QS-30), then both states are announced and visible as text (4.1.3, P-10). The visible text is an overlay above the bottom navigation that covers the page and never moves it (DS-54).
- Given I submit a form with errors, then the focus moves to the first invalid field or to an error summary that links each field, and every error message names the field and how to fix it (3.3.1, 3.3.3; DS-38).
- Given a photo of a species or specimen, then it carries an alternative text with the species or specimen name and the date; purely decorative images are hidden from assistive technology (1.1.1).
- Given a chart (growth trend, zone distribution), then the same values are available as text or a table, and an unknown value reads "unbekannt", never an invented number (1.1.1, 1.3.1, P-08).
- Given a status shown as color, emoji or icon (care phase, etiolation, overdue), then the same status is also given as text that assistive technology reads (1.4.1, 1.3.3).

### US-QS-11 · Keyboard shortcuts · 🟨 new

As a **plant keeper working at a desktop** I want to reach the frequent actions with shortcuts.

Acceptance criteria:

- Given any view, when I press `?`, then an overview lists every shortcut available in this view and globally; it is also reachable from the help entry (US-QS-09).
- Given the global shortcuts (starting set, assumption: go to Today, collection, Arten and wishlist; search; new measurement), then they come from one central register; every shortcut action is also reachable through a visible control, and that control shows its shortcut.
- Given a shortcut made of a single character, then I can turn it off or change it to one with a modifier in my account settings, and it never fires while the focus is in a text field (2.1.4).
- Given a shortcut, then it does not take over keys that browsers, the operating system or screen readers use (for example Tab, Ctrl+L, Alt+arrow, the screen reader modifier keys); the register rejects such a key at build time (guardrail).
- Given a phone without a keyboard, then nothing depends on a shortcut.

State of implementation (🟨, starting values and assumptions, decided within DS-70): the keys of the starting set are `?` (overview), `/` (search), `h` (Heute), `s` (Sammlung), `p` (Arten, the species mode of Sammlung) and `w` (Wunschliste); each is a single character, and its modifier variant is Alt+Shift with the same physical key. The keyboard shortcut mode is an account setting, `plain` (single characters work, starting value), `modifier` (Alt+Shift) or `disabled`; it is per account, so it applies on every device of the keeper (assumption), set under "Konto", then "Einstellungen", in the layer "Wie nutzt du die App?". The overview opens with `?` and from the help entry "Was die App kann". The register refuses Tab, Enter, Space, Escape, Backspace, Delete, Insert, Home, End, Page Up and Page Down, the arrow keys, CapsLock, NumLock, ScrollLock, Pause, Print Screen, the context menu key, Meta, OS, Control, Alt, AltGraph, Shift, Fn, Clear and F1 to F24, every Ctrl or Cmd combination, and Alt without Shift (menu access keys). "New measurement" is not a global shortcut: its control ("Messen") exists only inside a specimen's layer, where a measurement belongs to one specimen, so a global key has no target; it is left out until that layer registers its own shortcut. Open points for the next step: a manual keyboard walk in a browser, a screen reader run, and the axe and keyboard gates of the new register entry for the settings layer.

### US-QS-12 · Adaptable display · 🟨 new

As a **plant keeper with low vision** I want to enlarge and adapt the display without losing content.

Acceptance criteria:

- Given a width of 320 CSS px or a browser zoom of 400 % on a 1280 px window, then every view works without horizontal scrolling and without cut-off content (1.4.10, 1.4.4); data tables follow the card pattern (DS-24).
- Given user-set text spacing (line height 1.5, paragraph spacing 2, letter spacing 0.12, word spacing 0.16 times the font size), then no text overlaps or is cut off (1.4.12).
- Given the device in portrait or landscape, then every view works in both (1.3.4).
- Given the system setting "reduce motion", then animations and transitions are off or reduced to a fade (2.3.3; DS-19).

### US-QS-15 · One screen per layer · 🟨 new

As a **plant keeper** I want every main destination to fit on one screen and open its topics as layers above it, so that I find things without scrolling through a long page.

Acceptance criteria:

- Given a viewport of 360 x 640 px or larger (starting value, assumption), when I open a main destination, then its overview fits between the app bar and the navigation without page scroll (the overview itself never scrolls, only a marked list on it may, under the fixed-frame rule below; owner decision 2026-11-21, issue 2412) and shows a summary, the next action (P-09) and at most 6 entries into its topics (starting value, assumption).
- Given an overview, when I open a topic, then it opens as a layer above it (a bottom sheet below 768 px, a pane beside the list from 1024 px; a dialog in between); the address names the layer (`?sheet=<topic>`), so Back closes it and a reload or a copied link reopens it; focus moves to the layer heading and returns to the control that opened it when it closes; Escape closes it.
- Given a layer whose first control is destructive (such as "Freundschaft beenden" in "Meine Freunde"), when the layer opens at any width, then the focus is on its title and not on that control, so a stray Enter cannot end a friendship (P-10, issue 1028).
- Given a layer whose first control is a text field (the species search of "Neuer Wunsch"), when it opens at any width, as a sheet, a dialog or the desktop pane, then that field keeps the focus so I can type at once (owner decision 2026-10-31, issue 1104).
- **Scroll model (owner decisions 1 to 7 of 2026-11-21, issue 2412; they replace the paging of lists, the first-screen rule of 2026-11-20 and option (c) of #2339):**
  - Given any view at any supported size, when I open it or scroll in it, then the frame stays in place: the top bar, the bottom navigation (the side navigation from 768 px) and the primary action never move, the page itself never scrolls, and only the elements marked as scroll regions (`data-scroll-region`) scroll, inside the frame. ### US-QS-27 · The installed app takes a new version on its next start · 🟨 new

As a **plant keeper** I want the installed app to switch to a new version only when I start it again, so that no page reloads under my hands and no entry is lost, and I want to see what is new once after that start, so that I know what changed without reading a changelog.

Acceptance criteria:

- Given a new version was deployed while the app is open, when I keep using the open app, then nothing reloads by itself and no entry, form or layer is lost (US-QS-03, US-QS-07).
- Given the new version is waiting, when a view loads lazily while I keep using the open app, then it loads from the files of the version I am running, which the app keeps on the device for that purpose, so the view does not fail after a deploy.
- Given the installed app is closed and started again, when it starts, then the new version runs: a waiting version takes over only when no window of the app is open any more.
- Given an update takes over, when it activates, then the stored files of older versions are deleted from the device; no open window is claimed and nothing is skipped (no skip-waiting, no claim).
- Given the app is installed for the first time on a device (no earlier stored files), when the worker activates, then it claims the open windows, so the first session's lazy views are served from the stored files too.
- Known limit (accepted): a window opened while an older worker is still active runs the new HTML under that older worker until the next start. The files of the new version that the older worker does not hold then come from the network, so a lazy view loads only while the server still has its file (the server keeps the files of the current version).
- Given a request is a GET of a file under `/assets/` of the app's own origin, when the device keeps that file for the running version, then the stored copy answers it; when the copy is not there, then the network answers.
- Given a request is a navigation (a route or `index.html`), an API call, the worker script `/sw.js`, a request of another origin or a request that is not a GET, then the network answers it untouched.

- Given a development build, then no worker is registered; given a browser without service workers or a page that is not in a secure context, then the app runs as before.
- Given the registration of the worker fails, then the app works, the failure is written to the console and nothing is shown to the keeper as an error (P-10).

### US-QS-30 · The installed app works offline and sends what was logged once it is online again · ⬜ new

As a **plant keeper** I want the installed app to keep working without a network, so that I see the last data next to the plant and what I log there is not lost.

Decision (owner, issues 144 and 1687, 2026-11-07 and 2026-11-10): the offline criteria of US-QS-07 move here, release R2 (`16-releases-and-decisions.md`). Before building, the claimer of issue 1687 brings the cut to the owner: which writes can queue, conflicts, photos and storage limits.

Acceptance criteria:

- Given the app was used before and there is no network, when I open the app, then it shows the last loaded data.
- Given a write action is made without a network, when the network returns, then it is buffered and delivered once, without a duplicate entry (`US-QS-03`).
- Given the device is offline, when the offline state shows, then an overlay bar lies above the bottom navigation (below 768 px) or at the top edge (from 768 px), says what it means and covers the page without moving it; the page under it stays usable, because pointer input passes through the bar (US-QS-10, DS-54).
- Given the device is offline and writes are not queued on the device yet (issue 1687), when the offline state shows, then its text promises only what happens: some writes are sent once the network is back, the others wait for the network ("Manches wird gesendet, sobald du wieder online bist. Anderes geht erst wieder mit Verbindung.", owner decision 2026-11-14), and a write that fails for the missing network says so and that the input stays ("Keine Verbindung. Deine Eingabe bleibt hier stehen."), never that the server is down (owner answer Q-47, issue 1863, P-10).
- Given I am offline and the write action I use is not buffered (it needs the network), when the write action shows, then it is inactive and says why next to it ("Du bist offline. Das geht erst wieder mit Verbindung."), the text I entered stays, and a press does nothing; a write that US-QS-03 buffers stays active. Given the network is back, when the same screen shows, then the write action is active again without a reload (owner answer Q-47 step 2, issue 1863, SG-BTN-05, SG-STATE-05, P-10).

Related: FR-SOZ-03 (the friends' last loaded copy with its "Stand" date), US-ACC (switching between accounts works offline), issue 1409 (a retried write), issue 1688 (the new version on the next start) and issues 1692 and 1695, which need the worker too.

State of implementation (issues 1644 and 1863): the write actions that need the network say why inline (`needsNetwork` of `Button` and `Checkbox`; forms by their footer and submit); the offline state is an overlay bar above the bottom navigation (`OverlayNotice`, DS-54) that does not change the classes or the layout of `main`; the buffered and delivered notes of the announcer are overlays too. The request state (DS-09) keeps the cached rows with a note when the device is offline after an earlier load (tests named US-QS-30 in `request-state.test.tsx`). Not built yet: a start of the shell without a network and the queue of writes (issue 1687). The worker of US-QS-27 takes new versions only and has no offline mode.

### US-QS-31 · Empty states carry an illustration that fits the place · ⬜ new

As a **plant keeper** I want an empty view to show a drawing of what belongs there, so that I see at a glance what the place is for and the app does not look unfinished (P-09, US-QS-07).

Decision (owner, issue 1833, 2026-11-10, after the phone test of release 0.3.0): empty states get proper illustrations. Until now every empty state shows the same mark, the sprout emoji in a tile; the device draws an emoji, so it differs from phone to phone, and it says nothing about the place. Open for the owner before building: the drawing style (proposal: the line drawing of the sign-in page, ADR 0011), who draws the set, and the final list of motifs.

Acceptance criteria:

- Given a view or a list that is empty (no plants, no wishes, no equipment, no measurements, no friends, nothing due, no hits), when its empty state shows, then it carries a drawing from one family: one style, one line weight, the colours of the theme. The drawing is part of the app, not a character of the device, so it looks the same on every device.

### US-QS-32 · A phone screen follows one written style guide · ⬜ new

As a **plant keeper** I want every screen on my phone to look and behave the way I know from the other apps on it, so that I do not have to learn the app screen by screen (P-09, P-11).

Decision (owner, issue 1844, interview of 2026-11-10 and 2026-11-12, E-31 in `16-releases-and-decisions.md`): on phones the baseline is Apple's Human Interface Guidelines together with WCAG 2.2 AA. The rules are written down once, each with a stable ID, in `docs/guides/reference/style-guide.md`; a rule there replaces an older rule where the two disagree, and the guide lists what it replaces. The app does not follow the guide yet: the mobile design review records the gap as findings, and each fix is a ticket of its own. Release R2 for the guide; the fixes are placed when the review is done.

Acceptance criteria:

- Given a rule on the look or behaviour of a phone screen, then it stands in the style guide with a stable ID, a reason and, where it replaces an older rule, the name of that rule; an ID is never renumbered.
- Given the detail of an object (a plant, a species, a wish) or a topic that is read, when I open it on a phone, then it is a page with a way back, not a sheet; a sheet or dialog is only for a task with a clear end (fill in, pick, confirm).
- Given a list longer than the window on a phone, then it scrolls under the bars that stay in place, and it is not cut into pages with buttons.
- Given any page, then the top bar names that page, and the product name stands only on the entry page, the sign-in page, in "Konto" and on the splash of the installed app.
- Given the actions of a view, then at most one is a filled button, a secondary one has a soft fill without a border, a tertiary one is text only, and nothing that only navigates or counts is green.
- Given a form or a sheet on a phone, then "Abbrechen" and the confirming action sit in its bar, a date is chosen with the system date picker, and a setting that applies at once is a switch.
- Given a form in a bottom sheet on a phone, when it opens, then "Abbrechen" (leading) and the confirming action ("Sichern", "Anlegen", "Weiter", or the red "Konto in 7 Tagen löschen") at the trailing edge sit in one row, the sheet's bar, above the title and above the scroll region, with a 44 px hit area each; the title stands in the row below, so it fits at 200 % text and 360 px, where the action wraps below "Abbrechen"; the close X is gone because "Abbrechen" is the one close control; a sheet without such a form keeps its X (SG-SHEET-04, SG-SHEET-02, SG-TOUCH-01, issues 1861, 1941).
- Given a form in a dialog (from 768 px) or a pane (from 1024 px), then the same two buttons are the bar of the layer, pinned at its bottom under the scroll region (`data-layer-bar`), so the confirming action is always in view whatever the length of the form, as in a phone sheet; the bar is outside the scroll region, holds one pair, and its status line stands right under the pair; a layer without a form shows no bar (SG-SHEET-04, owner decision d-115, which replaces the plain row of d-060 for dialogs and panes only). Given the page form "Messen" or "Pflanze anlegen" from 768 px, then the pair is a plain, non-sticky row after the last field (owner decision d-060), only one pair is in the page, and the order of the DOM, and so of the focus, is the order of the picture.
- Given a form in a bottom sheet at 200 % text with the keyboard open (a window of 354 px), then the bar and the focused field are both in the window and neither covers the other: a sheet with bar actions in a window shorter than 16 rem (256 px at the default text size, 512 px at 200 %) drops its grabber and reads its title to assistive technology only (SG-FORM-02, WCAG 2.4.11, 1.4.4).
- Given the bar of a form, when I tap "Abbrechen" with typed input that is not saved, then the app asks "Eingabe verwerfen?" as it does for the close control, Escape and Back; without typed input it closes at once (SG-FORM-06). Given the confirming action, then it sends the form it belongs to, is inactive while nothing changed (owner answer Q-42) or while the write runs, shows the form's pending text and cannot be pressed twice, and keeps its current label and write behaviour.
- Given a form that is a page ("Messen", "Pflanze anlegen") below 768 px, then its bar is the first part of the form region, sticky at the top below the top bar, and "Abbrechen" leaves the page the way Back does. Given the keyboard opens on a phone and the visual viewport shrinks (for example from 716 to 354 px), when a field has the focus, then the bar follows the visual viewport, so "Sichern" and the focused field are both visible and neither covers the other; a focused field scrolls clear of the bar (SG-FORM-02, WCAG 2.4.11, issues 1895, 1889 (F-0091)).
- Given the care profile, then its "Sichern" is inactive while nothing changed and shows the primary fill (label 4.5:1, boundary 3:1) as soon as a value changed, never white on white (SG-COLOR-06, issue 1969).
- Given a one-tap write that changes what I see ("Erledigt" on "Heute" and in its layer, "Gegossen" and "Gießen" in the sheet and the plant layer, the bulk move "Alle n nach … umstellen"), when I tap it, then the changed row stays in its place for 8 s (starting value, assumption) as "<Ergebnis> · Rückgängig" ("Erledigt", "Gegossen", "Gegossen heute", "Umgestellt"), its result is announced, the rows below move only after the 8 s, and "Rückgängig" restores the state from before the tap through a validating operation (P-03); after the 8 s the undo is gone (SG-FEED-03, US-QS-32).
- Given the result of a write, then it shows at the place of the change and is announced to assistive technology (US-QS-10); no toast shows it, and undo is offered at the place of the change.
- Given content on a phone, then it is shown as flat grouped lists without a shadow; a shadow marks only what floats above the page.
- Given a case in which an older rule and the baseline disagree and the guide is silent, then the owner decides and the answer becomes a rule of the guide.

### US-QS-33 · Motion follows the device, with a switch in the app · 🟨 new

As a **plant keeper** I want short animations that show me what changed, and I want them to stop when my device asks for less motion or when I turn them off in the app, so that the app feels lively without making anyone dizzy.

Context: US-QS-12, US-QS-14 and the style guide (SG-MOTION-02, US-QS-32) already ask that motion stops under `prefers-reduced-motion: reduce`. No account setting for motion exists yet (checked in `01`, `14`, `20`, `22`). This story adds the in-app switch and defines **reduced motion** once (glossary in `00`): the device asks for it **or** the keeper chose "Bewegung aus" in the app. Every criterion in the specs that names `prefers-reduced-motion: reduce` or "reduced motion" applies to both. Calm mode (US-ACH-08) is a different thing: it hides achievements and celebrations and does not change the motion of the app.

Acceptance criteria:

- Given the purposeful motions of the app, then they include (starting list, assumption, decided by the PO): the change of view (US-QS-14), cards that enter a list (US-QS-14), a layer that opens or closes (US-QS-15), a new specimen that enters the collection after "Pflanze anlegen" (it rises into its place, and the place is where the plant now stands), and the card transitions of the suggestion deck (US-ENT-01, US-ENT-10) and of swap matching (US-TAU-02). Each follows the motion rules of the style guide (SG-MOTION-01 to SG-MOTION-08, US-QS-32): its durations, `transform` and `opacity` only, and it shows where something came from or went to. Nothing moves for decoration alone, nothing loops, and nothing blinks.
- Given a keeper who never opened the setting, when the device asks for reduced motion, then the app runs without motion; when it does not, the app runs with motion. Nobody has to look for a switch to get the behaviour of the own device.
- Given the account settings, layer "Wie nutzt du die App?" (US-QS-11), then a choice "Bewegung" offers "Wie auf dem Gerät" (default) and "Bewegung aus", with one line of help: "Aus: Ansichten, Karten und Ebenen wechseln ohne Animation. Alles bleibt erreichbar." (US-QS-15: at most one line).
- Given "Bewegung aus", then the app behaves exactly as under `prefers-reduced-motion: reduce` on every device of the keeper, also when the device does not ask for it: no route transition, no list entry, no sliding layer, no flying card; every state change is still shown at once (US-QS-14).
- Given "Wie auf dem Gerät" and a device that asks for reduced motion, then the app shows no motion; the app offers no choice that forces motion on against the device (assumption, decided by the PO: whoever set it on the device needs it).
- Given motion is reduced, then nothing is lost: every function, every text and every decision stays the same, the buttons and keys that stand beside a gesture stay (US-QS-08, US-ENT-01), a swipe still works where it worked, only without the card following the finger, and focus and announcements are the same as with motion (US-QS-10, P-10).
- Given I change the choice, when it is saved, then it applies at once on the open screen, without a reload, and a refused save keeps the old value and shows the error text (P-10).
- Given the app starts, when the account setting is not loaded yet, then the last choice known on this device applies; with none known, the device setting applies; no animation runs in the first frame that the setting would forbid.
- Given the sign-in pages before an account is known, then only the device setting applies.
- Given the choice is saved, then it goes through the same validating operation as the other account settings (US-ACC-02, P-03); a value outside the set is refused with `input.invalid` naming `motion`.

Status 🟨 (2026-11-12): the choice, its storage, the first frame, the sign-in pages and the reduced-motion rules for every existing motion (route transition, list entry, layers, the swipe card of US-ENT-01) are in place. Open: the rise of a new specimen into its place after "Pflanze anlegen" and the card stack of US-ENT-10 do not exist yet; they follow the same rules when they are built.

Assumptions, decided by the PO (revisable): the choice is stored per account, like the shortcut mode of US-QS-11, so it follows the keeper to every device; the value set is `system` (default) and `reduced`. The device keeps a copy of the last value only to avoid motion on the first frame; the account value wins once it is loaded.
