# PflanzenDex app

Monorepo (npm workspaces) with four packages. Every task runs through the `Makefile` in the repo root (`make help`). Tooling and docs are English; domain code uses the German glossary terms from the specs (`account`, `specimen`, `review_case`, …).

| Package         | Contents                                        | Rule                                                                                                                                            |
| --------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/core` | Domain logic, pure functions                    | imports nothing from API, web, database, file system or network (AB-1); every directory with code has an `index.ts`                             |
| `packages/db`   | PostgreSQL schema, migrations, tenant isolation | meant for `api` only; `core` and `web` never import it; every user-owned table carries `account_id` and calls `tenant_protection()` (FR-ACC-02) |
| `packages/api`  | HTTP API (Hono)                                 | calls `core` only through `@pflanzendex/core` (AB-2)                                                                                            |
| `packages/web`  | Mobile-first PWA (React, Vite)                  | calls `core` only through `@pflanzendex/core` (AB-2)                                                                                            |

## Modules (ADR 0003, variant A)

Inside each layer package the code is cut into module folders with the same names: `src/<module>/` in `core`, `db`, `api` and `web`. Each module has an `index.ts` as its public interface; other modules and the layer root import only from there. Test files sit next to the code. Migrations stay one global sequence (`packages/db/migrations/`, files `0001`-`0004` keep their names).

| Module       | Contents                                                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kernel`     | Operation engine, `Result`, error codes, validation, ports (`core/src/kernel`, with `meta`); tenant access, migrations, idempotency (`db/src/kernel`); error mapping (`api/src/kernel`) |
| `account`    | Sign-in and account (`core/src/account`, `db/src/account`, `api/src/account` incl. `auth/`, `web/src/account`); tables `account_data`, `account_role`                                   |
| `catalog`    | Review status (`core/src/catalog`, `db/src/catalog`); table `review_case`                                                                                                               |
| `light`      | Light zones and locations (`core/src/light`, `db/src/light`, `api/src/light`, `web/src/light`); tables `lightZone`, `location`                                                          |
| `collection` | specimens (`core/src/collection`, `db/src/collection`, `api/src/collection`, `web/src/collection`); table `specimen`; depends on `kernel`, `catalog`, `light`                           |
| `care`       | Care phases (`core/src/care`, `api/src/care`, `web/src/care`); no table yet (derived live); depends on `kernel`, `catalog`, `light`, `collection`, `monitoring` (registered)            |

```bash
make setup   # install dependencies
make dev     # start API (port 3000) and web (Vite)
make ci      # all gates: lint, types, boundaries, format, tests, build
```

- **Node:** version 24 (`.nvmrc`). Vitest 5 does not officially support odd Node versions (e.g. 25).
- **TypeScript 6.0.x** is pinned on purpose: `typescript-eslint` does not support TypeScript 7 yet (peer range `<6.1`).
- **Boundary check:** `npm run boundaries` (script and tests in `scripts/`); messages name the rule ID, file and line. Module rules AB-7 to AB-14 (FR-QG-19) read the module register `modules.config.mjs`; AB-10 and table ownership run in `findSchemaViolations` (db tests).
- **Thresholds** (starting values, assumptions, E-15): file length ≤ 200, complexity ≤ 15, in `core` ≤ 10 (`eslint.config.js`).

## Database and tenant isolation (TE-02)

- **Test database:** `make db-up` starts PostgreSQL 16 in Docker (port 54329; `make test` and `make ci` do this themselves, in CI it runs as a service). Another server: `PFLANZENDEX_TEST_DATABASE_URL`.
- **Test database owner (#294, QG-D1):** `PFLANZENDEX_TEST_DATABASE_URL` is the cluster superuser, which bypasses row-level security. The `db` suite therefore does not use it: the vitest global setup (`packages/db/src/test-global-setup.ts`) creates the login role `pflanzendex_test_owner` (no superuser, no BYPASSRLS) and the database `<name>_owner` it owns, and every test connects with `openOwnerPool()`, so row security applies to every query as in production. The superuser is used only where a test deliberately works across tenants or needs superuser-only settings: `openFixturePool()` (fixture helpers in `src/fixtures.ts`, cleanup and observation of forced tables in tests, the `observer` argument of `checkTenantIsolation`) and `openAdminPool()` (scratch databases and roles). `rls-guard.test.ts` fails if the suite connection ever becomes a superuser. The `api` suite does the same (#476): its vitest global setup (`packages/api/src/test-global-setup.ts`, #485) creates the owner role first, its test files open `openOwnerPool()` plus `openFixturePool()` for setup, cleanup and cross-tenant observation; `packages/api/src/rls-guard.test.ts` fails if the api suite connection becomes a superuser.
- **Migrations:** SQL files in `packages/db/migrations/`, forward only, with a checksum (an applied file must never change). Apply with `make migrate`.
- **New user-owned table:** column `account_id uuid not null references account(id) on delete cascade`, then `select tenant_protection('table');` and an entry in `packages/db/src/<module>/fixtures.ts` (aggregated in `packages/db/src/fixtures.ts`). If any of these is missing, the generic test (`tenant.test.ts`) fails. Tables without an account (e.g. the species catalog) need an entry with a reason in `WITHOUT_ACCOUNT_ID`.
- **Access:** only through `withAccount(pool, accountId, …)`: a transaction, role `pflanzendex_app` (without BYPASSRLS), session variable `app.account_id` for that transaction only.

## Sign-in (US-ACC-01, E-03)

- **Local auth server:** `make auth-up` starts Keycloak 26.8 (port 18081, realm `pflanzendex`, imported from `app/dev/keycloak/pflanzendex-realm.json`) and a mail catcher (Mailpit, http://localhost:18025). The target generates a random admin password into `app/dev/.env` (not in the repo). `make auth-down` removes both, including their data.
- **Theme and scope:** the realm uses the login theme `pflanzendex` (`app/dev/keycloak-theme/`, mounted by `app/dev/compose.yaml`, tokens of the web app, favicon included; #205). The web client has `fullScopeAllowed: false`; the audience mapper keeps the API token valid. Access tokens live 5 minutes (ADR 0009).
- **Redirect ports:** the realm allows port 5173. A worktree runs on its own port: `cd app && node tools/keycloak/web-port.mjs` adds `PFLANZENDEX_DEV_WEB_PORT` of `.env.worktree` (or the ports given as arguments) to the web client through the admin API; run it after `make auth-up` (idempotent; #202).
- **Flow:** the web app redirects to Keycloak with the OIDC authorization code flow and PKCE (sign-in and registration happen there, in German). Keycloak first requires email confirmation, then setting a password (policy: at least 10 characters). Passwords never reach us (FR-ACC-03).
- **API:** `Authorization: Bearer <access token>`; signature (JWKS), issuer and audience `pflanzendex-api` are verified. Every request sets the account via `withAccount`. `GET /account` returns the caller's own account data. Environment: `OIDC_ISSUER`, `OIDC_AUDIENCE`, `DATABASE_URL`, `WEB_ORIGIN`.
- **Account creation:** `findOrCreateAccount` (db) is the dedicated path for the first sign-in: the `anmeldung_*` policies on `account` show and allow only the row of the verified subject (`app.subject`). No BYPASSRLS.
- **Web:** `VITE_OIDC_AUTHORITY`, `VITE_OIDC_CLIENT_ID` and `VITE_API_URL` override the defaults. "Sign out on all devices" calls the Keycloak account API (`DELETE /account/sessions`).
- **Tests without Keycloak:** token, middleware and UI tests run without the auth server (locally generated keys). The flow against Keycloak was checked manually: `Docs/test-logs/acc-01.md`.

## Operator role and review status (TE-08)

- **Roles:** table `account_role` (`operator`, `reviewer`), granted only through admin access, never through the application (the application role has no rights on the table; it only reads its own role through `roles_of_account()`). A role grants no access to other accounts' content (P-04).
- **Review status:** table `review_case` (creator = `account_id`, object as `object_kind` + `object_id`, status `proposal`, `ai_unreviewed`, `curated`, `reviewed`, `rejected`). Operations in `core/src/catalog`: `catalog.propose` (anyone), `catalog.kuratieren` and `catalog.review` (reviewers only). A database trigger enforces the same rights as well.
- **The only exception to tenant isolation:** reviewers read the review queue (`review_case`, metadata only). The tenant test proves that an operator sees nothing of other accounts in any other table (`review.test.ts`).
- **Species catalog:** since BES-01, `art` references `review_case` (see below). Approval only with all required fields filled (FR-BES-14); merging and notes to the creator belong to BES-10. An AI connection never gets a role and therefore cannot approve anything (FR-BES-06).

## Access by invitation only (US-ACC-05)

- **Data:** migration 0018 (`-- module: account`): `invitation` (SHA-256 hash of the code, expiry as `timestamptz`, `redeemed_at`), `access_setting` (one row, `invitation_only`, default off) and `account_data.last_active_at`. Neither new table has an `account_id`: both are justified entries in `WITHOUT_ACCOUNT_ID`, have row security enabled without any policy (`ENABLE` only, not `FORCE`: the `security definer` functions run as the table owner and must keep working if the owner is not a superuser), the application role has no right on them (like `account_role`) and reaches them only through `security definer` functions that check the operator role again (`is_operator()`): `create_invitation`, `list_invitations`, `set_invitation_only`, `operator_overview`; `redeem_invitation` (needs the verified subject of the registration path) and `invitation_required` need no role.
- **Monthly operating cost (migration 0021):** `operator_cost` (one row, like `access_setting`: `amount_cents`, `currency`, `month`, all null until the operator enters a figure) is another justified entry in `WITHOUT_ACCOUNT_ID` with row security on and no policy; the operator reaches it only through `set_operator_cost` and `operator_cost`, which check `is_operator()` again and refuse a month after the current one (UTC). `operator_overview` is unchanged, so the previous app version keeps working; core derives the cost per user (`costPerUser`, rounded half up to whole cents, unknown without a figure or without active accounts).
- **Codes:** `newInvitationCode` (`core/src/account/invitation-code.ts`) turns 15 bytes from the injected CSPRNG (`crypto.randomBytes` in the API) into 24 Crockford base32 characters (120 bits), shown as six groups of four. The code is returned once by `invitation.create`; only its hash is stored, so a leaked database holds no codes. Lookup is an equality match on the hash (no secret-dependent comparison in application code). Typed codes are normalized by a linear scan (case, spaces, hyphens, `O`/`I`/`L`), never by a pattern on user input. `invitation.create` is marked `secret` (`Operation.secret` in `core/src/kernel/operation.ts`): its answer is never written to the `idempotency` table and the key is released after the run, so a repeat with the same `Idempotency-Key` creates another single-use code instead of replaying the old one (tested by querying the table). Calls that are still running stay guarded by `idempotency.in_progress`.
- **Single use:** `redeem_invitation` is one conditional update (`redeemed_at is null and expires_at > now()`); concurrent redeems wait for the row lock and then find it used (tested with 20 parallel registrations of one code: exactly one account). The account is created in the same transaction (`AccessPostgres.register`); a subject that already has an account (or gets one from a concurrent request) rolls everything back and keeps the code unused. Expiry is an UTC instant, compared with the database clock.
- **Registration gate:** `authentication` calls `admitAccount`: a known subject always gets its account; an unknown one only while `invitation_only` is off. Otherwise every protected route answers 403 `invitation.required` and creates nothing. `POST /registration/invitation` (`{ code }`, bearer token, no account needed) registers the subject: 200 `{ registered }` or 403 `invitation.invalid`, the same answer for an unknown, used, expired or malformed code (no oracle). This one write has no `Idempotency-Key` (there is no account yet); it is naturally repeatable. There is no rate limit (120-bit codes cannot be guessed); a per-subject limit can be added with the general API rate limits. `createApp({ invitationOnly })` forces the mode per app instance (tests only: they must not flip the shared setting).
- **Operator area (operator role only, not reviewers):** `GET /operator/overview` (`accounts`, `activeAccounts` (opened the app within `activeWindowDays` = 30, assumption), `costPerUser` (always `null` = "unbekannt", there is no cost measurement, P-08), `invitationOnly`, `invitations` with state `open|redeemed|expired`, never a code or a person), `PUT /operator/registration` (`{ invitationOnly }`, `Idempotency-Key`, operation `registration.set_mode`), `POST /operator/invitations` (`{ validForDays }` 1 to 30, default 7, `Idempotency-Key`, operation `invitation.create`, 201 with the code once). `GET /account` has a new hint `operator` (the UI shows the tab "Betreiber"; the operations check the role again). `last_active_at` is set whenever the account loads `GET /account`.
- **No content for the operator (P-05):** the overview functions return counts only; no row rule is opened by the operator role (tested by scanning the policies), and the operator account reads no foreign row of any tenant table (tested as a sweep).
- **Web:** after sign-in, a 403 `invitation.required` shows the form "Einladungscode" (`InvitationPage`); the tab "Betreiber" (`OperatorPage`) shows counts, the mode in words with its one action, the code form with the new code once, and the invitation list.
- **Limits:** the operator role is assigned by hand (`account_role`), as before. Closing self-registration at the sign-in service (Keycloak) is a realm setting outside the app.

## Locations and light zones (US-LIC-05)

- **Data:** tables `lightZone` and `location` (migration 0004), both with tenant isolation and names unique per account (case-insensitive). A location references its zone through the composite foreign key `(account_id, light_zone_id)`: a zone of another account cannot be assigned, and renaming never changes an assignment. A location without a zone is allowed and shows up in `GET /hints`.
- **Operations (`core/src/light`):** `lightZone.create|update|remove|defaults`, `location.setUp|update`. Writes only through `execute` with the `Idempotency-Key` header; replay protection lives in the `idempotency` table (24 hours, an assumption).
- **API:** `GET/POST /lightZones`, `PUT/DELETE /lightZones/:id`, `POST /lightZones/defaults`, `GET/POST /locations`, `PUT /locations/:id`, `GET /hints`, `GET /lightZones/ableitung?lightDemandLux=&standardLevel=&weichesBlatt=` (US-LIC-01: derives the Lichtzone of a species from its lux need and the account zones, read-only, never stored). Errors: `{ error: { code, text, details?, data? } }`.
- **Limit (deleting a zone):** the `ZoneUsage` port asks every source which of them uses a zone. Today the only source is "locations". species link no zone (the zone is derived, FR-BES-10). **specimens (BES-02) link no zone either**: they reach one only through their location, which the location source already reports, so no extra source is needed yet. **The first specimen field that points at a zone (the override for cuttings, BES-04, and the care profile, BES-09) has to bring its source** (parameter `additionalUsage` of `lightRoutes`, implemented by `collection` for its own table, never by SQL on `specimen` from `light`), otherwise it would go unnoticed when a zone is deleted. The mechanism is tested with a stub. Locations cannot be deleted yet (no criterion).
- **Hints:** LIC-05 shows its hints (locations without zone) on its own page and provides them through `locationHints` (`GET /hints`). The central page for incomplete specimens is US-BES-08 (below).

## Species catalog (US-BES-01)

- **Data:** migration 0005: `art` (profile per DM-BES-01) and `species_name` (Latin, German and English name, synonyms, each with a normalized search key). Every species has exactly one review process (composite foreign key `(object_kind, id)`, `on delete restrict`: deleting an account never takes a catalog species with it). The catalog has no `account_id`: both tables are justified entries in `WITHOUT_ACCOUNT_ID` and also listed in `CATALOG_TABLES`, for which the generic schema test demands enforced row rules.
- **Visibility (FR-BES-11):** everyone sees a species when its process is `curated` or `reviewed`, otherwise only its creator (also `rejected`). `species_status()` (`security definer`) decides, because `review_case` hides other accounts processes; for that, only the owner role may read approved processes (policy `katalog_freigegeben`). `ai_unreviewed` stays private unless an operator batch creates it. The application has only `select` and `insert` on `art` (insert only with an own process); there is no update or delete. Reviewers do not see private proposals yet (that view belongs to BES-10).
- **Operation:** `art.propose` (`core/catalog/art`) creates species, names and the `proposal` process in one transaction. Duplicates (same normalized Latin name or synonym among the visible species) return `art.duplicate` with the existing species and write nothing. Private proposals of different accounts are not duplicates (the error would reveal foreign data); BES-10 merges them.
- **Required fields of a proposal (assumption):** Latin name, difficulty 1-3, default level 2-4, light need (lux), growth measure, etiolation signs, success criteria. Everything else is optional and shown as "unbekannt" when missing (P-08); the dormancy period only counts as a pair. A source for light need and dormancy is required only for approval (FR-BES-14).
- **API:** `GET /species?q=` (partial word, accent- and case-insensitive, at most 50 hits, names the name it matched), `GET /species/:id` (foreign or unknown species: 404), `POST /species` (`Idempotency-Key`).
- **Limits:** the catalog stays empty until the catalog job (POK-03) or operator batches fill it. The hand-over to the AI client (US-KI-08) is missing. "Diese Art wählen" hands the species to the Bestand tab (US-BES-02, below). Image, traits, versions (FR-BES-12) and editing an own proposal do not exist yet. Species link no light zone (FR-BES-10), so they need no `ZoneUsage` source; care profiles (BES-09) and the zone override of cuttings (BES-04) will.

## Guided onboarding and start page (US-ACC-03)

- **Derived, not stored:** `onboardingSteps`, `startAction` and `onboardingHints` (`core/src/account/onboarding.ts`) compute from three counts (locations, light zones, specimens) what the account still lacks. No table, no API route, no migration.
- **Web:** the new tab "Start" is the landing view. A new account without a specimen is led through three steps (locations, light zones, first plant); each step can be skipped, and the wizard starts at the first step the account has no data for. The steps reuse the forms and cards of `light` (`LocationsStep`, `ZonesStep`; the zones step takes over the default levels, edits, deletes or adds zones, and assigns a zone to a location). Moving to a new step moves the focus to its heading; the step marker is a polite live region. "Einstieg beenden" leaves the guide for good on this device (no way back inside the app); the first-plant step leads to the catalog (US-BES-02). The app composes the modules in `start-page.tsx` and `onboarding-wizard.tsx` (the modules do not know each other).
- **After skipping:** the start page shows a hint per missing detail (never an error) and, without a specimen, the next action "Art im Katalog wählen".
- **Limit:** "skipped everything" is remembered per account in the browser's `localStorage` (a per-device convenience, assumption); on another device the guide is offered again. It is only shown while the account has no specimen.

## Specimens (US-BES-02)

- **Data:** migration 0007 (`-- module: collection`): table `specimen` with `account_id` and a row rule (generic tenant test plus fixture `FIXTURES_COLLECTION`), the name unique per account (case-insensitive), `caught_at` as `date` (a local calendar day, read back as text, never as a `Date`), `status` (`plant`, `cutting`, `archived`), `location_id` empty = "unbekannt". Migration 0006 (`-- module: light`) only adds `unique (account_id, id)` on `location`, the target of the composite foreign key `specimen_location (account_id, location_id)` (AB-10, AB-14: a migration touches only the tables of its module, so the licht change is its own file).
- **Art reference (AB-10, global reference table):** `specimen.species_id` has the plain foreign key `specimen_species` to `art(id)` with `on delete restrict` (migration 0008). `art` has no `account_id`, so it is registered in `GLOBAL_REFERENCE_TABLES` (`modules.config.mjs`, with owner and reason); the gate allows such a key only from a module that may depend on the owner, only to `(id)` and only with `on delete restrict`. The database refuses an unknown species and the deletion of a species in use; the operation still reads the species through the catalog (`SpeciesSource`) under the caller's account, so private proposals of other accounts stay `art.not_found`. The application role still cannot delete species. Tests needing a species use `createFixtureSpeciesAt` (`db/src/fixtures.ts`).
- **Operation:** `specimen.create` (`core/src/collection`). Only the species is required (plus the time zone of the profile, US-ACC-02; the device's zone only as fallback). Name by DM-BES-03 before saving: species name (German, else Latin; assumption), with a marker `Species – marker`. A taken name writes nothing and returns `specimen.name_taken` with the existing specimens of the species (the database unique index decides, no pre-check race). `Gefangen_Am` is `localToday(uhr, timeZone)` (`kernel/date.ts`, NFR-08). The time zone comes with the request: the web app sends the one of the profile (US-ACC-02), the device's zone only as fallback while none is chosen.
- **target location (limit):** the port `TargetLocationSource` (defined in `collection`, to be implemented by `care`) is asked for the location of the species for today. Without phase logic (PHA) and care profile (BES-09) nothing implements it: `NO_TARGET_LOCATION` answers "unbekannt" and the location stays empty unless the keeper chooses one of their own. Nothing is invented (P-08). A chosen location wins over the port.
- **measurement series and treatment list:** returned as empty derived lists (`measurements: []`, `treatments: []`), no columns, no tables; WAC and BEH bring their own.
- **API:** `GET /specimens`, `GET /specimens/:id` (foreign or unknown: 404 `specimen.not_found`), `POST /specimens` (`Idempotency-Key`; body `speciesId`, `timeZone`, optional `marker`, `locationId`). Errors: `specimen.name_taken` 409, `art.not_found` and `location.not_found` 404.
- **Web:** tab "Bestand"; "Diese Art wählen" in the catalog opens the form for that species (the app wires `catalog` and `collection`, the modules do not know each other).
- **Limits:** no editing of location, status or other fields and no deleting (renaming by marker: US-BES-03; archiving: US-BES-07); addition, zone override, provenance and sharing fields of DM-BES-02 are missing; no specimen hints yet (BES-08).

## Correct the catch date of a specimen (US-BES-11)

- **Data:** no migration; `caught_at` (`date`) is the only column that changes.
- **Operation:** `specimen.correct_catch_date` (`core/src/collection/create.ts`, input `specimenId`, `timeZone`, `catchDate`) applies the rules of the creation (FR-BES-04): `calendarDateField` (a calendar date from 1900-01-01 on, else 400 `input.invalid` on `catchDate`) and "not after today in the keeper's time zone" (`specimen.caught_in_future` 400 on `catchDate`). Its own port `CatchDateStore.setCaughtAt` writes one statement; on an archived specimen a date after `archived_at` changes nothing (`specimen.caught_after_archived` 409), archiving date and reason stay. A foreign or unknown specimen is 404 `specimen.not_found` (P-04). The Pokédex catch date is derived from the stored value (US-POK-07), nothing else is written.
- **API:** `POST /specimens/:id/catch-date` (`Idempotency-Key`; body `timeZone`, `catchDate`).
- **Web:** the card has "Fangdatum"; the form shows the stored date ("Bisher: …" or "unbekannt"), is preset to it (today when unknown), limited to today, and after saving the message names the specimen and the new date (P-09); a refusal marks the field (P-10).
- **Limits:** the archive section has no entry point yet; an archived specimen can be corrected through the API only.

## Tell several specimens of a species apart (US-BES-03)

- **Data:** migration 0013 (`-- module: collection`): unique index `specimen_marker_per_species (account_id, species_id, lower(marker))` for rows with a marker; archived specimens count, their marker stays taken like their name (US-BES-07). The name was unique per account already, so no existing data can violate the index.
- **Naming rule (DM-BES-03), `core/src/collection/shared/markers.ts`:** the 1st specimen is plain; a further one needs a marker (`specimen.marker_required` 409, with name and existing specimens; before US-BES-03 this case was `specimen.name_taken`). The marker is unique per species, case-insensitive (`specimen.marker_taken` 409). From the 3rd **active** specimen on, every active specimen has a marker: `specimen.create` returns `specimen.markers_missing` 409 (data `missing: [{id, name}]`, nothing written) until the request carries `markers: [{specimenId, marker}]` for each of them; those renames and the insert run in one transaction (`SpecimenStore.create(…, assignments)`). An answer for a specimen that is not missing (also a foreign one) is 404 `specimen.not_found`. Archived specimens do not count and are never renamed (their name and marker stay taken).
- **Rename:** operation `specimen.mark` (`POST /specimens/:id/marker`, `Idempotency-Key`, body `marker`): sets marker and name (`Species – marker`) in one statement. The ID, location, date and status stay, so renaming changes no references (the name is display text). Empty marker is 400 `input.invalid`, a taken one `specimen.marker_taken`, an archived specimen `specimen.archived` 409, a foreign or unknown one 404 (P-04). The name is derived from the species' current display name; the marker of the specimen itself may change case. Changing the location of an existing specimen is **not** part of this story (follow-up, PHA-03).
- **Web:** the form preselects the marker "Klammer" from the 2nd specimen on (only a preset, not applied if a specimen carries it already) and asks for the markers existing specimens miss before it sends anything; the card has "Kennzeichen" to give or change a marker (form with name preview; message "… heißt jetzt …", errors stay visible). `SpecimenCard` carries `speciesId` and `marker` for this.
- **Limits:** restoring an archived specimen can leave three active specimens with one unmarked (the rule is checked when creating and renaming, not when restoring); the preset "Klammer" is a UI default, the API requires an explicit marker.

## Create a cutting and pot it (US-BES-04)

- **Data:** no migration. `status` already knew `cutting` (0007, renamed in 0012). Cutting light is **derived** (P-01): the lowest zone of the account (`cuttingLight` in `core/src/collection/placement/cutting-light.ts`, the same rule as the count in `zoneDistribution`), so there is no stored zone override to delete when potting.
- **Operations:** `specimen.create` takes an optional `status` (`plant` default, or `cutting`; anything else is 400 `input.invalid`). A cutting without a chosen location gets the location of the growth phase from the port `TargetLocationSource.growthLocation` (also in the dormancy phase), a plant the target location as before; without an answer the location stays "unknown" (P-08). `specimen.repot` (input `specimenId`) turns a cutting into a plant in one statement; a plant or archived specimen stays unchanged (`specimen.not_a_cutting` 409), a foreign or unknown one is 404 `specimen.not_found` (P-04).
- **API:** `POST /specimens` accepts `status`; `POST /specimens/:id/repot` (`Idempotency-Key`, empty body). The card shows the lowest zone as light zone for a cutting; the phase list and the zone distribution already left cuttings out.
- **Web:** checkbox "Das ist ein Steckling" in the form, button "Eingetopft" on cutting cards, message and error text after the action (P-09, P-10).
- **Limits:** the feed event "Eingetopft" for shared specimens needs SOZ and sharing, which do not exist yet; there is no per-specimen zone field (BES-04 in DM-BES-02) because the zone of a cutting is derived. ## Care phases (US-PHA-01)

- **Derived, never stored (P-01):** `carePhasesList` (`core/src/care`) reads the specimens and their species and computes the phase per request: rest phase when today (`localToday(uhr, timeZone)`, the user's time zone, NFR-08) lies in the species' `Von…Bis` (month-day, both ends inclusive, may span the new year), otherwise growth phase. Only specimens with status `plant` whose species has a dormancy period are listed (cuttings and archived ones are not).
- **API:** `GET /carePhases?timeZone=<IANA name>` returns `{ phasen: [{ specimenId, name, speciesId, phase, locationId, targetLocationId }] }` sorted by name; a missing or invalid time zone is 400 `input.invalid` with the field `timeZone`. The time zone comes with the request: the web app sends the one of the profile (US-ACC-02), the device's zone only as fallback while none is chosen.
- **Web:** tab "care phases", with an empty state that says what to do next (P-09).
- **Limits:** the target location per phase belongs to the keeper's care profile (BES-09, missing), so `targetLocationId` is always `null` ("unbekannt", P-08); `TargetLocationSource` (FR-PHA-05) is not implemented yet. A dormancy period on the specimen itself (override) does not exist. The E2E flow with an specimen waits for a fillable species catalog; E2E covers the empty state.

## Specimen cards (US-BES-06)

- **What:** `GET /specimens/cards?timeZone=Europe/Berlin` returns one derived card per own specimen (no table, no migration): name, species name, status, location, light zone (the zone of the location; a zone override on the specimen comes with BES-04), last measurement, photo, and the earliest open treatment with "+N weitere". A missing or unknown time zone is `input.invalid` (400); "today" is the local date in that zone (NFR-08). The route sits before `/specimens/:id`.
- **Ports (module `collection`, registered in `modules.config.mjs`):** `MeasurementSource` (last measurement and youngest photo per specimen) and `TreatmentSource` (open treatments, `care`/BEH). Both are asked once for all own specimen ids, never for foreign ones. `care` implements `MeasurementSource` (`measurementSource` in core, `MeasurementStore.lastFor` in db, wired in `createApp` via `measurementSourceFor`): the cards show the last measurement; the photo stays empty until US-WAC-05. `care` also implements `TreatmentSource` (`treatmentSource` in core, `TreatmentsPostgres.open` in db, wired in `createApp` via `treatmentSourceFor`, US-BEH-01): cards show the next open treatment and "+N more". `NO_TREATMENTS` stays the null implementation for `specimenRoutes` used without `care` (tests). `createApp` takes `measurements` and `treatments` options to replace them (tests).
- **Unknown stays unknown (P-08):** a species the account cannot see, a location without zone or a missing location is `null` and shown as "unbekannt". Etiolated growth ("Vergeilt/dünn") is shown as a warning, never as success.
- **Web:** tab "Bestand" shows the cards in a grid (`repeat(auto-fill, minmax(min(100%, 16rem), 1fr))`: one column on narrow phones, more when there is room); the note of the last measurement is a native `<details>`; the photo is a link that opens it large.
- **Limits:** photo, measurement and treatment data appear only once WAC and BEH implement the ports (the card logic is tested with stubs); archived specimens are hidden (BES-07).

## Archiving specimens (US-BES-07)

- **Data:** migration 0011 (`-- module: collection`): nullable columns `archived_at` (`date`, read back as text, NFR-08), `archived_reason` (1 to 250 characters, a start value) and `status_before_archiv` on `specimen`, plus the check `exemplar_archiv_zusammen` (status `archived` if and only if date and reason are set). `status` already knew `archived` since 0007. No new table, so no new tenant fixture; the row rule of `specimen` covers the new columns.
- **Operations:** `specimen.archive` (input `specimenId`, `timeZone`, `reason`; the date is the local calendar date of the time zone) and `specimen.restore` (input `specimenId`; restores the status from before, so a Steckling stays a Steckling). Both run in one statement. Archiving twice keeps date and reason of the first archiving (`specimen.already_archived` 409), restoring a non-archived one is `specimen.not_archived` 409, a foreign or unknown specimen is 404 `specimen.not_found`. Measuring an archived specimen is refused with `specimen.archived` 409.
- **API:** `POST /specimens/:id/archive` (`Idempotency-Key`; body `timeZone`, `reason`), `POST /specimens/:id/restore` (`Idempotency-Key`), `GET /specimens/archived` (`{ archived: [{ id, name, speciesName, caughtAt, archivedAt, archivedReason }] }`, newest first). `GET /specimens` and `GET /specimens/cards` leave archived specimens out (the ports of BES-06 never hear their ids); `GET /specimens/:id` still returns them with date and reason.
- **For later evaluations:** every derivation over specimens filters with `isActive` from `core` (distribution, treatments, Pokédex ownership, today list). Care phases already list only `plant` (FR-PHA-04).
- **Web:** button "Archivieren" on each card opens a form (reason from a list or free text), the section "Archiv" below the list shows reason and date with "Wiederherstellen". Success and errors stay visible (P-09, P-10).
- **Limits:** the name of an archived specimen stays taken (assumption: restoring can then never collide), so a new specimen of the same Art needs a marker. Archiving on a swap (US-SOZ-11) comes with SOZ. The measurement history of an archived specimen is readable over the API but has no screen.

- **Data:** migration 0014 (`-- module: collection`): table `care_profile` (key `(account_id, species_id)`, tenant isolation with fixture, registered in `modules.config.mjs`). Every column is a deviation; `null` means "the catalog applies", so an empty profile is valid. Locations and the zone hang on the own account through composite foreign keys `(account_id, id)`; the species through the plain key `care_profile_species` to `species(id)` (`on delete restrict`), the second user of the registered global reference table (AB-10). Dormancy from/until are a pair (check), watering intervals 1 to 365 days (assumption).

- **Web:** tab "Pflegeprofil" (`CareProfilePage` in `web/src/collection`): per species catalog value and my deviation per field, choices from the own locations and zones, month/day selects for dormancy, "Auf Katalog zurücksetzen" per field, success and refusals stay visible.
- **Limits:** no hint on catalog changes (FR-BES-12, no catalog versions yet), no wish trigger (WUN), watering intervals are stored but read by nobody until US-MON-05, the specimen card does not use the zone override.

## Pokédex ownership (US-POK-06)

- **What:** `GET /pokedex/ownership?timeZone=<IANA>` returns `{ ownership: { caught, unidentified } }` (400 `input.invalid` without a valid zone; the web sends `currentTimeZone()`: profile zone, device zone as fallback), derived live (no table, no migration, P-01). `speciesKey` (`core/src/pokedex`) takes the first two words of the Latin name, skips the hybrid sign (`Citrus x limon` is `Citrus limon`), lowercases the epithet and returns the addition (`var.`, `subsp.`, `f.`, `'Cultivar'`) as chip. A species is caught when at least one active specimen of the own account refers to it (`isActive`: cuttings count, archived ones do not, US-BES-07). Every caught entry has `species`, `speciesId`, `source`, `genus`, `chips`, `specimenCount` and `caughtDate`, sorted by name.
- **Catch date (US-POK-07):** `caughtDate` is `{ date, source }`, the earliest date across all active and archived specimens of the species. Per specimen: `caught_at` (`source` `caught_at`, exact), else the creation moment (`created_at`, exposed as `SpecimenRow.createdAt`) converted to the local calendar date of `timeZone` (`source` `created_at`, shown as "≈"), else `{ date: null, source: "unknown" }` ("Datum unbekannt"). Never guessed (P-08); an archived specimen counts for the date, not for ownership. The photo (latest measurement photo, Wikipedia image) is missing until WAC-05 and POK-03.
- **Not counted, but named (P-10):** a specimen whose Latin name has no epithet (`Hippeastrum`, `Parodia sp.`) or whose species the account cannot read lands in `unidentified` with `text` and `nextAction` "Bestimme die Art, dann zählt es." (P-09).
- **Module:** new `pokedex` module (`core`, `api`, `web`), edges `kernel`, `catalog`, `collection` as registered in `modules.config.mjs`; it reads through the existing ports (`SpecimenStore`, `SpeciesSource`), no new edge.
- **Search, filter, sort (US-POK-08):** each caught entry also carries `germanName`, `familyLatin`, `familyGerman` (from its species, `null` = unknown) and `genusSpeciesCount` (always `null` until the taxonomy build, US-POK-03, no number is invented). `browsePokedex` (`core/src/pokedex/browse.ts`) is pure view logic: case-insensitive search over species, German name, genus and family; filters `all`, `caught`, `species_poor` (known genus count up to 10); sorts `family` (groups, unknown family last, `total` `null` without a tree), `alphabetical`, `catch_date` (newest first, undated after) and `species_count` (ascending, unknown last).
- **Web:** tab "Pokédex" (`PokedexPage`): number of caught species, search field, filter buttons (chosen one marked; "Fehlend" and "Artenarm" disabled with the reason while catalog tree and genus counts do not exist), sort selection, a card per species with German name, genus, chips, catch date and number of specimens (grouped and collapsible by family on request), "Keine Art gefunden." with a reset, and the list "Noch nicht gezählt".
- **Details (US-POK-09):** each caught entry carries `speciesId` (the plain species represents the card, a cultivar only until a plain one appears) and `source` (the catalog's source field, `null` = unknown). A tap on a card (`PokedexCards`, name button stretched over the card) opens `SpeciesDetail`, which replaces the list (at most one open; "Schließen" or Escape closes it, focus returns to the card; `use-detail.ts`). It shows name, genus, family, status, specimen count, chips, catch date and the source (a link only for http(s) addresses). Image and short text are shown as unknown until the taxonomy build (US-POK-03); Missing cards and their actions (wishlist, friend) do not exist yet. "Zum Artprofil" calls `onOpenSpecies(speciesId)`; `App` wires it to the catalog: `SpeciesPage` takes `openId` and starts on that profile.
- **Limits:** the catalog accepts only `Genus epithet 'Cultivar'`, so a chip comes from a cultivar today; `var.`, `subsp.` and `f.` belong to the specimen extra (DM-BES-02), which does not exist yet. There are no collector cards (number, photo) yet: they need the catalog tree (POK-01, POK-03).
- **Rank and progress (US-POK-10):** `collectorProgress(caught, tree)` (`core/src/pokedex/rank.ts`) is pure and derives the rank from the number of caught species (Keimling 0-4, Setzling 5, Jungpflanze 15, Blüher 30, Baumkrone 60, Botaniker 100), the species missing until the next rank and the bar fraction. Total, percentage and orders come from the taxonomy tree (US-POK-03), which does not exist yet: they are `null` and the web (`pokedex/collector-rank`) shows "unbekannt" and says why (P-08). No API change: the web computes it from `ownership.caught`. Assumption, decided by the PO: the bar shows progress from the current to the next rank.
- **Milestones (US-POK-11):** `milestones(tree, caught)` and `milestoneOverview` (`core/src/pokedex/milestones`) are pure: family (discovered, connoisseur with half rounded up, complete), genus (discovered, complete) and the explorer over orders, each with `current`, `target`, `remaining`, up to 3 missing species and the date of the nth catch (`null` as soon as one date is unknown, P-08). - **Web:** tab "Wunschliste" (`web/src/wishlist`). Pictures are **not loaded**: a keeper-typed address would make every viewer's browser contact a third-party host (P-05), so the card shows only a link "Bild ansehen (öffnet extern)" with the source until pictures are saved locally (US-WUN-04). - **Replenishment warning (US-WUN-02):** `GET /wishes/candidates` also returns `replenishment: { buffer, zones, actions, nextAction }`: every zone 2 to 4 with fewer open candidates than `buffer` (starting value 2, a constant until an account setting exists) appears in `zones` with `{ zoneId, name, open, text }` ("Nachschub nötig: <zone> (N offene Kandidaten)"); wishes without a zone 2 to 4 count towards no zone (FR-WUN-03). `actions` says which follow-up actions exist (`discover`: US-ENT-07, `suggestions`: US-WUN-04; both `false` today), `nextAction` is `null` without a warning. Derived live, nothing stored.
- **Purchase (US-WUN-03):** `POST /wishes/:id/buy` (with `Idempotency-Key`, no body) runs `wish.buy`: an open wish becomes `bought` in one statement and leaves the candidate list; nothing is deleted. The answer is `{ wish, changed, hint }` with what happened and what to do next. Buying a bought wish again answers 200 with `changed: false` and writes nothing (idempotent, also for two racing calls); a discarded wish is refused with 409 `wish.not_open`; an unknown wish or one of another account is 404 `wish.not_found`. `GET /wishes/bought` returns the history `{ bought, hint }` (bought plant wishes by name). - **Duplicate names (FR-WUN-06, #303):** `GET /wishes/candidates` also returns `duplicates` (open wishes without a name key, which migration `0020` left exempt from the unique name rule) and `duplicateHint` (`null` when there are none). `POST /wishes/:id/rename` (body `{ name }`) runs `wish.rename`: the new name gets its key and must be free (`409 wish.name_taken`, also for the unchanged name). `POST /wishes/:id/remove-duplicate` runs `wish.remove_duplicate` and deletes the wish. Both work only on wishes of the own account that have no key; any other wish is `409 wish.not_duplicate`, an unknown or foreign one `404 wish.not_found`. Both need an `Idempotency-Key`. The page shows the hint above the candidates with a rename field and a confirmed delete per wish. No migration.
- **Path to the plant and discard (US-WUN-05):** `wish.link_specimen` (`POST /wishes/:id/specimen`, body `{ specimenId }`, `Idempotency-Key`) links a bought wish to the specimen it became: `409 wish.not_bought` for an open or discarded wish, `409 wish.already_linked` when the wish has another specimen or the specimen another wish, same pair again `200` with `changed: false`, a wish or specimen of another account `404`. Migration `0024_wishlist_wish_specimen.sql` adds the nullable `wish.specimen_id` with the composite foreign key `(account_id, specimen_id)` to `specimen`, a check that only a bought wish carries a link and a partial unique index (a specimen belongs to one wish). Expand only, no policy or grant change. `wish.discard` (`POST /wishes/:id/discard`) sets an open wish to `discarded` (kept, idempotent; `409 wish.already_bought` for a bought one); `GET /wishes/discarded` lists the discarded wishes. The two writes are not one transaction (`specimen.create` lives in `collection`, ADR 0003): the app (`web/src/wish-to-specimen.tsx`) creates the specimen first and links afterwards, shows a failure and offers a retry. Web: "Exemplar anlegen" after "Gekauft" and in the bought list finds the species by the wish name (exact Latin name), opens the creation form with it, or opens the catalog search with the name.
- **Limits:** no way back from "bought" or "discarded" (US-ENT-04), no purchase date or price (the cost view US-EQU-09 does not exist, nothing is invented), no species field on the wish (the specimen link carries it), no hint list for wishes outside zones 2 to 4 yet.

- **Module:** new platform module `jobs` (`core/src/jobs`, `db/src/jobs`, `api/src/jobs`), registered in `modules.config.mjs` with the edge `kernel` only; MON, POK and KI will depend on it, never the other way. ADR 0003 O-1 had put the queue into `kernel` until it grows rules of its own; the lease, retry and merge rules are that growth (assumption, decided by the PO; revisable).
- **Port `JobQueue`** (`core`): `enqueue`, `claim`, `succeed`, `fail`, `counts`, `purge`; time always comes in as a parameter (no I/O in `core`). `enqueueJob` validates and merges, `runNext` / `drainJobs` run due jobs through handlers (`<module>.<job>` to a function). Contract test `queue.contract.test.ts` (in-memory adapter); the PostgreSQL adapter `JobsPostgres` repeats the cases and adds concurrency.
- **Repeatable (US-QS-03):** an open job with the same type and dedupe key is merged (unique index in the database); handlers must be repeatable. A failed run is retried with backoff (30 s doubled, at most 1 h, 5 attempts: starting values, assumption); a job without attempts left, or of a type without handler, ends `dead` with its last error and stays visible (P-10). A worker that vanished loses its job after the lease (5 min, assumption) and another worker takes it over; a late result of the old worker is ignored. A job that did not start before `expiresAt` becomes `expired` and never runs late. Finished jobs are purged after 30 days (assumption).
- **Data:** table `job` (migration `0022_jobs_queue.sql`), installation-level, **without account id** (justified entry in `JOBS_TENANT_EXCEPTIONS`): the application role has no rights on it, only the worker (owner connection) does; the payload holds ids, and a handler reaches user data through `withAccount` (P-04). Claiming uses `for update skip locked`.
- **Runner:** `createJobWorker` (`api/src/jobs`) polls every 5 s (assumption) inside the API process (one deployable); a queue error is reported to stderr and retried at the next tick. Handlers are registered in `api/src/jobs/handlers.ts` (empty until the first job type exists).
- **Open:** no job types yet (reminders US-MON-08, catalog build US-POK-03, photo processing US-WAC-05, AI orders KI), no queue figure in the health endpoint (US-DEV), no retry or release of dead jobs by the operator.
