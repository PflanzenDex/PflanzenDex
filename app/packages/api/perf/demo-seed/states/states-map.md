# Demo seed: where each feature state can be seen

Covers the feature inventory of 2026-10-30: 83 features, 375 states, of which 160 were not in the demo seed. The states
profile (`DEMO_SEED_PROFILE=states`, see `docs/guides/reference/app.md`, "Demo seed") makes 36 of the 160 reachable
and 2 more partly. 3 need no seed data, 2 are in the default seed or follow from its values, and 117
stay manual with the reason given in their row. Tracked in #1072 (US-DEV-01).

## Statuses

- `profile`: created by the states profile. `states/states-profile.test.ts` proves the data through the API of the acting
  account and the owner connection. How the screen renders it is not checked on the running app by this mapping.
- `partial`: the profile covers part of the state; the row says which part.
- `base`: the default seed creates it or it follows from the seed values. Check it on the app (the row says "verify").
- `steps`: no seed data needed; read only, or an action that writes nothing (the row describes it).
- `manual`: the seed cannot make it. The row gives the reason. Most of these are writes that belong on a throwaway
  account, refusals, browser or device permissions, external services, or a fresh account.

## Accounts

- Anna (`test`): style few, calm mode on, three plants and one received cutting.
- Ben (`test2`): style many, 50 specimens, lamps, treatments, care profiles, friend of Clara.
- Clara (`test3`): style many, friend of both, offers and wishes. With the profile she is also reviewer and operator.
- "new account": a fresh account with no data. The seed does not create one (see "Fresh accounts" below).

## What the profile changes in the base seed

- Anna declines Ben's friend request. Ben's request to Anna was pending in the base seed; after the profile it shows as
  declined on Ben's side. Pending on both sides exists only in a database made by the base seed alone.
- Ben's Pilea cutting keeps its open request from Clara (base state). The Dracaena cutting Ben hands over is created by
  the profile, so a second base run does not clash with a handed-over row.
- Clara's Hoya cutting: Ben's request is accepted and Clara confirms her side only (one-sided handover).
- Clara has the reviewer and the operator role. Anna's deck gets two decisions (Yes, No).
- Demo values are assumptions, not measured data: prices, the Hoya kerrii light need, the proposal source
  "Demo-Quelle (Annahme)", the lux reading. They are marked as such in the code and in the UI texts they feed.

## Fresh accounts (manual)

The dev realm has three users: `test`, `test2` and `test3`. Account rows are keyed by the Keycloak subject, so a fresh
account the browser can sign in to needs a new Keycloak user. The seed does not create realm users, and the owner rule
for agents forbids changing them. A person registers one account through the sign-up page of the dev realm, then signs
in. The states that need it are the onboarding guide, the locked-function pages on a new account, the empty states and
the invitation-only sign-in page.

## Known issues

- A re-seed after a realm re-import fails with `correction.duplicate_open` (base seed: the open correction of the old
  account is still there). Reset the worktree database and seed again.
- Running the seed in a worktree: the admin password is read from `KC_ADMIN_PASSWORD`, then from `app/config/dev/.env`,
  then from the main checkout's file. The last lookup joins an absolute git common directory onto the app path, so it
  finds no file in a worktree. Set `KC_ADMIN_PASSWORD` in the environment or give `DEMO_SEED_SUBJECTS=test=<sub>,test2=<sub>,test3=<sub>`.
  Recorded here, not changed in #1072.
- The profile is safe to run again on the same database (the test runs it twice and compares all counts).

## Run

    cd app
    PFLANZENDEX_ENV=local DATABASE_URL=<worktree database> DEMO_SEED_PROFILE=states npm run seed:demo -w @pflanzendex/api

Only on a worktree database (never the shared dev database, never the test host). Without `DEMO_SEED_PROFILE` the
default seed runs as before.
